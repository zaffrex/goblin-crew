## 배경 (Context)

진마씨가 세 판(`magpie_nest` → `park_fountain` → `laundromat`)을 하고 답했다(`#goblin-ceo` 2026-11-28): 세 번째 판 적당, 웃긴 곳 없음, "왜 이렇게 클리어했는지 잘 모르겠다. 퍼즐 요소가 전혀 없다", "처음의 건조기가 왜 이렇게 동작하는지 이해 못 했다". 그리고 "눈에 보이는 아이템1을 조작해서 변화, 다음에 아이템2를 조작해서 1이랑 결합해서 아이템3으로 퍼즐을 푸는 요소가 전혀 없고 너무 단순해."

숫자로 봐도 맞다(조사 #1033 3절, #1035 3~4절).

| | 원작 1~3편 12화면 (중앙) | 우리 3화면 |
|---|---|---|
| 물건을 쓰는 단계 | 12/12화면, 4.5번 | 0 |
| 물건 변화 / 결합이 있는 화면 | 9/12 / 8/12 (둘 다 5/12) | 0 / 0 |
| 정답 행동 수 | 12 | 3~4 |
| 의존 깊이 | 7 | 2~3 |
| 한 층 폭 ≥2 | 10/12 | 2/3 |
| 같은 변화 규칙을 두 번 쓰기 | 4/12 (Theo 재셈, #1035 리뷰) | 0 |
| "왜"를 성질 한 문장으로 설명 | 6/12 | 0/3 |

원인은 ADR-0018이다. 1절이 퍼즐을 **능력 매트릭스**(어떤 능력이 몇 화면에서 필수인가)로만 정의했고, 정답 길 모양은 M6(경고) 하나뿐이었다. 그래서 "맞는 특기를 맞는 곳에 한 번" × 3~4가 매트릭스를 통과했다. 그 뒤 ADR-0422·0761과 화면 설계는 반응과 웃음만 고쳤고 퍼즐 몸통은 한 번도 보지 않았다. 설계 쪽 원인은 #1033 3-2절에 적었다: 고리마다 그 화면만의 버릇(스누즈 관리인, 역회전 건조기)을 새로 발명해서, 놀랍지만 앞으로 추론할 수 없었다.

퍼즐 설계 원칙이라 L2다. 다음 화면 설계와 Theo 인벤토리 작업이 이 결정에 걸려 있다.

제약: 사용량(#117)이 빠듯하다. 엔진에 인벤토리 UI가 없다(6-4-6은 방향만). 아이템 칸 자리는 x 404~480, 24px 칸 3개다(Luna, #1031). 조작은 "얼굴 고르기 → 물건 누르기 한 번"(진마씨 11/18). 휴대폰은 아직 판정 전이다(#935).

## 고려한 선택지 (Options)

### A. 물건 사슬이 몸통, 능력은 고리를 여는 손 (추천)
일반 화면의 정답 길을 "줍기 → 변화 → 결합 → 쓰기" 사슬로 만들고, 셀 수 있는 숫자로 검사한다. 특기는 물건의 성질을 바꾸는 공통 손이 된다.
- 장점: 진마씨 문장 모양 그대로다. 원작 분포(물건 사용 12/12)와 맞는다. "성질 두 개로 한 문장"이 진마씨 ③ "왜"에 바로 답한다. 엔진은 장치 안 결합까지 지금 규칙 모양으로 된다(Theo 장난감 화면: 행동 10, 깊이 5, 노드 50, 86ms, #1035 리뷰).
- 단점: 인벤토리 UI·입력이 새로 든다(Theo). 그림이 첫 화면 25~35칸 ≈ 8~11h 늘어난다(Luna). 빨래방을 다시 짜면 역회전 줄 약 47칸이 버려질 수 있다. 조작이 한 단계(물건 들기) 늘어난다. M2가 늦어진다.

### B. 능력 퍼즐 그대로 + 화면당 아이템 단계 1개
- 장점: 싸다. 인벤토리 칸 1개와 `item` 동사 하나면 된다.
- 단점: 원작 최소치(사용 ≥1, 중앙 4.5)에도 못 미친다. 행동 4~5, 깊이 3이면 "너무 단순해"가 그대로 남는다. 진마씨가 짚은 변화·결합이 없다.

### C. 능력을 아이템으로 바꿈 (특기 대신 도구)
- 장점: 사슬이 가장 순수해진다.
- 단점: 세 사람 구분이 사라진다. ADR-0003 세계관과 "능력의 엉뚱한 사용"(우리 기준의 앞 반쪽)을 버린다. 게임 콘셉트 근본 변경에 가까워 L3 위험이 있다.

## 결정 (Decision)

**A를 채택한다.** 숫자는 시작값이다. 첫 적용 화면의 Mia 블라인드와 진마씨 플레이 뒤 다시 본다.

### 1. 퍼즐의 정의 (ADR-0018 1절 첫 문단을 바꾼다)
- **화면 퍼즐 = 물건 사슬.** 플레이어는 화면에서 물건을 줍고, 성질을 바꾸고, 합쳐서, 막힌 곳에 쓴다.
- **능력은 고리를 여는 손이다.** 특기는 정답 버튼이 아니라 물건이나 장치의 성질을 바꾸는 수단이다. ADR-0018 M1~M5(능력 필수·비율)는 그대로 두고, 이 ADR의 C1~C9가 그 위에 얹힌다.
- **고리 종류** (설계 문서 고리 표와 검사가 같은 말을 쓴다):

| 고리 | 모양 | 데이터에서 셈 (Theo 확인 필요, 2절 T1) |
|---|---|---|
| 줍기 | 화면 속 물건 → 인벤토리 | `do.give`가 있고 `when.item`이 없는 규칙 |
| 변화 | 물건 + 능력 또는 장치 → 성질이 바뀐 물건 | 한 규칙이 물건 X를 `take`하고 X의 다른 상태 X′를 `give`. 또는 장치에 넣고(플래그) 꺼낼 때 X′ |
| 결합 | 재료 2개 이상 → 새 물건 하나 | 장치·NPC 안 합치기: 재료마다 `item` 넣기 규칙(`take` + 플래그) → 모으는 규칙이 플래그 전부를 보고 `give` |
| 쓰기 | 물건 → 막힌 곳 | `verb: "item"`이고 `when.item`이 있는 규칙 |
| 내주기 | 물건 → NPC·동물이 움직임 | 쓰기의 한 종류로 센다 |

- 한 행동에 고리 종류가 둘 붙을 수 있다(예: 물건을 장치에 넣기 = 쓰기 + 결합 재료). 행동 수는 행동 하나로 센다(Theo #1035 리뷰 2번).
- **손에서 물건 둘 합치기는 이번 ADR에서 쓰지 않는다.** `Action.target`이 spot/hotspot만 받고, 물건 → 물건 입력·BFS 행동 수 items²가 같이 온다(Theo #1035 리뷰). 결합은 장치·NPC 안에서만 한다.

### 2. 숫자 원칙 (C = chain)
"일반 화면"은 튜토리얼이 아닌 화면이다. 지금 `magpie_nest`만 튜토리얼이다.

| # | 원칙 | 검사 | CI |
|---|---|---|---|
| C1 | 일반 화면 `solution`에 **쓰기 ≥3** (튜토리얼은 ≥1) | `solution` 리플레이에서 쓰기 규칙 수 | 실패 |
| C2 | 일반 화면 `solution`에 **변화 ≥1, 결합 ≥1**, 그리고 변화된 물건이 결합 재료다(진마씨 "1 변화 → 2와 결합 → 3으로 푼다") | 리플레이에서 변화 규칙이 `give`한 물건이 결합 재료 규칙의 `when.item`에 있나 | 실패 |
| C3 | **성질 한 문장.** 사슬 고리마다 설계 문서 성질 표에 "A는 ~하고 B는 ~하니 ~"가 한 문장으로 적힌다. 클리어 직전 마지막 고리는 반드시 | 설계 리뷰(사람). 한 문장이 안 되는 고리는 리뷰에서 막는다 | 사람 |
| C4 | **특기 = 공통 성질 손.** 특기마다 물건에 주는 변화를 모든 화면 공통 표(`docs/design/ability-property-table.md`, 이 ADR 머지 뒤 Kai)로 고정한다. 그 화면만의 NPC·장치 버릇에 기대는 고리는 화면당 **≤1**. `solution`의 능력 동사 단계는 전체의 **≤50%** | 버릇 ≤1은 설계 리뷰. 비율은 `solution` 동사 집계 | 사람 / 경고 |
| C5 | **규칙 재사용.** 처음 보여 준 변화 규칙을 정답 길에서 **≥2번**(두 번째는 다른 물건에) 쓴다. 처음은 놀람, 두 번째는 플레이어가 앞으로 추론한다(우리 기준 "알고 나면 당연한"의 뒤 반쪽) | 규칙에 묶음 키(Theo 제안 `law`)를 달고 `solution`에서 같은 `law` 수를 센다 | 경고 (키가 붙으면 실패로 올림) |
| C6 | **모양: 퍼졌다 모이기.** 일반 화면 의존 깊이 **≥5**, 한 층 폭 **≥2**, 최단 정답 **8~12행동**. ADR-0018 M6의 "일반 화면 4~10"을 이 값으로 바꾼다(튜토리얼 2~4는 그대로) | BFS 최단 길이 + `solution`의 `when` 의존으로 층 계산(Theo, T4) | 경고 |
| C7 | **무차별 대입 상한.** 도달 가능한 어떤 상태에서도 인벤토리 물건 **≤2**(칸은 3개라 1칸 여유). 화면에서 줍는 물건 **≤5** | BFS 모든 노드의 인벤토리 크기 최댓값 | 실패 |
| C8 | **틀린 조합은 성질을 가르친다.** 그럴듯한 오답 조합 3개를 설계 문서 첫 시도 표에 적고, 반응이 "어떤 성질이 모자란지"를 보여 준다. 정답 예고편은 금지(기준 [기록](../decisions/2026-11-22-puzzle-unexpected-but-obvious.md) 그대로). 맞는 재료·틀린 순서에는 "거의 맞음" 반응을 따로 둔다 | 설계 리뷰 + Mia 기록 | 사람 |
| C9 | **둘이 같이 타이밍 고리 ≤1.** 한 번 누르기 입력이고 휴대폰이 이미 상한에 걸려 있다 | 설계 리뷰 | 사람 |

- C1·C2·C7은 구조라서 실패로 둔다. C5·C6은 원작에서 가져온 추정치라 경고로 시작한다. 경고가 나면 PR에 이유를 적고 머지할 수 있다(ADR-0018 1절 CI 구분과 같은 방식).
- **"왜" 기준은 원작보다 높다.** 원작도 6/12화면만 성질 한 문장으로 설명된다. 진마씨 ③ 때문에 우리는 C3을 모든 고리에 건다. 대신 우리 특기(쿵·장대·소리)는 물리라서 마법류보다 맞추기 쉽다(#1035 4절 3번).

### 3. 막다른 상태와 세이브 (Ben 반대 반영)
- **S3는 그대로이고 물건 소모를 포함한다.** 지금도 `bfs.ts` `deadEnds`가 "도달한 모든 상태에서 클리어에 닿나"를 보고 `check.ts` `reportErrors`에서 실패다. 재료를 넣어 없앤 뒤 막히는 상태도 여기서 잡힌다.
- **노드 수를 화면 리포트에 늘 적는다.** 물건 상태가 늘면 `maxStates` 100,000 한도에 걸려 S3 판정 불가 = 실패가 된다(ADR-0096 7). 화면 JSON PR은 리포트의 노드 수를 PR 본문에 적고, 1만을 넘으면 설계를 줄일지 Theo와 본다.
- **화면 안 사슬 상태는 저장하지 않는다.** 새로고침하거나 이어 하면 그 화면 입구에서 다시 시작한다. 화면 하나가 8~12행동이라 다시 해도 1~2분이다. 세이브 스키마(`src/core/save/schema.ts`)는 바꾸지 않는다.
- **화면 사이로 물건을 넘기지 않는다.** 앞 화면 물건이 다음 화면 필수 재료가 되는 설계는 이번 ADR에서 금지한다(Theo T6, 세이브 v2·화면 순서가 엮임). 원작 7/12가 들고 오지만, 넣을 때는 새 ADR + Ben 세이브 v2다.

### 4. 입력 (방향만, 숫자·구현은 Theo 1라운드로 채움)
- 기본안은 [ui-interaction.md 6-4-6](../design/ui-interaction.md): 아이템 칸을 누르면 "든 상태", 다음에 누른 장치·핫스팟에 쓴다. 메뉴는 다시 넣지 않는다(진마씨 11/18).
- 특기로 물건을 바꿀 때: 든 물건을 **고른 사람의 특기로** 장치에 쓴다(예: ズッシー를 고르고 물건을 든 채 장치를 누르면 쿵이 물건에 들어간다). Theo가 "얼굴 고르기 → 물건 누르기 한 번"과 어떻게 맞출지 답한다.
- 휴대폰 칸 크기(1.0배 CSS 약 33px < 44px)는 Theo 실측으로 정한다(Luna 우려).

### 5. 그림 비용 (Luna 1라운드 그대로)
- 공통 1회 11칸 ≈ 4h(인벤토리 틀 3, 묵직이 `hold` 2, 성질 효과 물방울·반짝·김 6). 성질은 물건마다 상태 그림을 따로 그리지 않고 **공용 효과 시트**로 얹는다.
- 화면당 14~24칸 ≈ 4~7h. 첫 화면 합 25~35칸.
- 16×16 아이콘은 성질 차이가 명도 한 단계라, 물건 라벨(성질 낱말 포함)은 빼지 않는다.
- ADR-0422 R1 상한은 세 화면 다 이미 넘었다(50·54·84 > 48). R1' 상한을 다시 정하는 건 이 ADR에 넣지 않고 Luna가 ADR-0422 개정으로 숫자를 낸다(회고 #2 A1 #1028과 같은 때).

### 6. 첫 적용과 순서
1. 이 ADR 머지.
2. 특기 성질 공통 표(Kai, C4) + Theo 인벤토리 입력·검사(C1·C2·C7) 나란히.
3. 첫 적용 화면 설계 문서(Kai) → Luna 칸 수 리뷰 → 그림·JSON → Mia 블라인드 → 진마씨.
- **첫 적용 화면은 PM이 정한다.** Kai 추천은 빨래방 다시 짜기다: 방·세탁기·건조기·자판기 그림을 다시 쓰고, 기계를 다들 아는 성질(적신다·말린다·내준다)대로 쓰면 장치 쪽 새 칸이 거의 0이다(Luna). 진마씨 ③ "건조기가 왜"에 같은 방으로 답할 수 있다. 대신 역회전 줄 약 47칸이 정답 길에서 빠질 수 있다.
- `magpie_nest`는 튜토리얼 예외(C1 ≥1)로 지금은 안 고친다. `park_fountain`은 첫 적용 화면이 통한 뒤 다시 본다.
- 설계 PR 리뷰어는 #1035 6절 "닮음 검사 목록"과 겹치는지 본다. 사슬 모양은 장르 관습이라 쓰고, 원작의 구체 조합은 쓰지 않는다(CLAUDE.md IP 가드레일).

### 7. ADR-0761(웃긴 박자)과의 관계
- 웃긴 박자 H1~H7은 그대로 둔다. 박자 자리는 사슬이 정해진 뒤 다시 센다. 웃음은 변화·결합 **결과 칸**(물건이 우스꽝스럽게 바뀌는 순간)과 틀린 조합(C8)에 놓는 것을 기본으로 한다.
- ADR-0761 개정(회고 #2 A1, #1028)은 이 ADR 뒤에 한다.

## 반대 의견 (Dissent)
- **Ben (반대 담당, 회의 1라운드)**: "되돌릴 수 없는 막다른 상태(소프트락)와 세이브. 지금 BFS 검사(M6)는 시작점→클리어 경로 존재만 봄." → 앞 문장의 사실은 다르다. S3 검사(`deadEnds`)가 이미 모든 도달 상태를 보고 CI 실패다. 대신 그 지적에서 진짜 위험(상태 수 증가 → 판정 불가 = 실패)을 3절 노드 수 보고 줄로 받았다. 세이브 쪽 "화면 중간 상태 저장 여부 결정"은 그대로 받아 "저장 안 함, 화면 입구 재시작, 화면 사이 물건 없음"으로 적었다.
- **PM (회의 안건)**: "인벤토리 UI가 '얼굴 고르기 → 물건 누르기 한 번' 결정과 부딪힌다. 조작이 한 단계 늘어난다." → 받아들인다. 4절은 방향만 두고 Theo가 답한다. 조작이 늘어나는 건 피할 수 없고, 메뉴를 다시 넣지 않는 선에서 6-4-6 "든 상태" 하나로 줄인다.
- **Luna (회의 1라운드)**: 아이템 칸이 딱 3개, 휴대폰 탭 33px. → C7을 "≤2"로 두어 칸 하나 여유를 남겼다. 탭 크기는 Theo 실측.
- 가장 강한 반론 (B 쪽): "엔진·그림이 드는 A보다, 아이템 단계 1개만 넣고 진마씨께 빨리 다시 보여 주자." 답: 원작에서 물건 사용이 가장 적은 화면도 1번이고 중앙은 4.5번이다. 한 단계만 넣으면 행동 4~5, 깊이 3이라 진마씨가 이미 "너무 단순해"라고 한 숫자 안에 남는다. 진마씨께 같은 답을 두 번 받는 비용이 엔진 작업보다 크다.

## 결과 (Consequences)
- 좋아지는 것: 퍼즐 몸통을 셀 수 있게 된다(C1·C2·C7 CI). 특기 성질 표가 화면 사이에 공통이라 플레이어가 앞 화면에서 배운 것으로 다음 화면을 추론한다(C4·C5). "왜"가 설계 문서 한 문장으로 리뷰된다(C3).
- 나빠지는 것: Theo 인벤토리 입력·검사 작업, 첫 화면 그림 25~35칸, 빨래방을 다시 짜면 약 47칸 손실. M2 날짜가 늦어진다(PM이 ADR 정리 때 숫자로 낸다). 화면 하나의 행동이 2~3배가 되어 Mia·진마씨 플레이 시간도 늘어난다.
- 새 리스크: (1) 물건이 늘어 무차별 대입(들고 있는 것 × 누를 곳 다 눌러 보기)이 생긴다 → C7·C8. (2) 성질 한 문장(C3)이 사람 검사라 설계자가 스스로 통과시킬 수 있다 → Mia 블라인드 "누르기 전 예상" 줄로 판정한다. (3) 원작 숫자를 기준으로 삼아 모양이 원작에 가까워질 수 있다 → #1035 6절 닮음 검사. (4) 휴대폰 인벤토리 칸이 손가락에 작다.
- 다시 검토할 조건: 첫 적용 화면에서 (1) 진마씨가 다시 "단순하다"고 하면 C1·C6 하한을 올린다. (2) Mia가 무차별 대입으로 풀면(오답 조합 시도가 정답 행동의 3배를 넘으면) C7을 줄이거나 C8을 강화한다. (3) 노드 수가 1만을 넘는 화면이 나오면 BFS 상태 키(ADR-0096)를 다시 본다. (4) 화면 사이 물건을 넣고 싶어지면 새 ADR.
