# ADR-0005: MVP는 서버 없이 localStorage 세이브로 간다

- 상태: 제안됨
- 날짜: 2026-11-15
- 작성자: **[BE Ben]**
- 리뷰어: FE Theo, Infra Sam (PM Noah 승인 대기)
- 관련: 이슈 #6

## 배경 (Context)
M2(퍼즐 3~5개 + 세이브 + 모바일 터치)에 서버가 필요한지 결정한다. 제약: 월 비용 0원(비용 발생 시 L3), 팀 운영 부담 최소, 개인정보 수집 최소. 현재 계획된 기능은 진행 상황 저장뿐이고 계정·리더보드 요구는 없다.

## 고려한 선택지 (Options)
### A. 서버 없음 + localStorage 세이브 (+ 파일 내보내기/가져오기)
- 장점: 월 0원, 운영·보안·개인정보 부담 없음, 오프라인 동작, 구현 1~2일.
- 단점: 기기 간 동기화 없음, 브라우저 데이터 삭제 시 소실, 플레이 통계 수집 불가. iOS Safari는 장기 미사용 시 저장소를 정리할 수 있음.
- 월 비용: **0원**

### B. 서버리스 (Cloudflare Workers+KV/D1 등 무료 티어) 클라우드 세이브·통계
- 장점: 기기 간 세이브, 어느 퍼즐에서 막히는지 익명 통계.
- 단점: 익명 ID/토큰 설계, 레이트 리밋, 남용 방지 필요. 무료 티어 초과 시 비용 발생(→ L3). 개인정보 고려 필요. 운영 대상이 늘어남.
- 월 비용: 무료 티어 내 **0원**, 초과 시 발생 (한도 모니터링 필요)

### A'. IndexedDB (참고)
- 50KB 미만이면 localStorage로 충분하다. IndexedDB는 비동기 API·트랜잭션으로 복잡도만 늘고, 축출(eviction) 정책은 localStorage와 같다. 채택하지 않는다.

### C. 자체 API 서버 + DB
- 장점: 자유도 최대.
- 단점: 호스팅 비용(대개 유료), 운영·백업·보안 부담. MVP 대비 과함.
- 월 비용: **0원 초과 가능성 높음** → 추천 시 L3

## 결정 (Decision)
**A를 채택한다.** 근거: M2 요구가 "세이브"뿐이며 localStorage로 충족된다. 서버가 가치를 주는 기능(동기화, 통계)은 MVP 성공 조건이 아니다. 저장 접근은 `SaveStore` 인터페이스 뒤에 두어 나중에 B로 교체할 수 있게 한다.

### 세이브 데이터 (JSON, 키: `goblincrew.save.v1`)
```json
{
  "version": 1,
  "contentVersion": "m2-1",
  "updatedAt": "ISO-8601",
  "progress": { "solvedScreens": [], "currentScreen": "s01" },
  "checkpoint": { "screenId": "s01", "gauge": 100, "activeCharacter": "c1", "carriedItems": [] }
}
```
- **`checkpoint` 하나만 저장**한다(화면 입장 시점 기준). 화면 내부 플래그·캐릭터 위치는 저장하지 않고, 화면에 다시 들어가면 화면 데이터로 초기화한다. 퍼즐 설계가 바뀌어도 세이브가 깨지지 않는다. 중간 상태 저장이 필요해지면 `checkpoint.screenState`를 추가한다(`version` 2).
- `gauge`(공용 체력/기력), `activeCharacter`, `carriedItems`(화면 사이에 들고 가는 인벤토리)는 최상위 자리만 잡아 둔다. **게이지가 화면 입장 시 리셋되는지 이어지는지 등 의미는 디자인 이슈 #3 결과를 따른다.**
- `unlockedScreens`는 저장하지 않는다. `solvedScreens`와 화면 연결 데이터로 계산한다(같은 사실을 두 곳에 저장하면 어긋난다).
- `contentVersion`: 스키마 `version`과 별개로, 화면 ID 변경/삭제 시 콘텐츠 마이그레이션 판단에 쓴다.
- **설정은 별도 키** `goblincrew.settings.v1`(`volume`, `textSpeed`). 새 게임 시작이나 손상 세이브 백업 시에도 설정이 유지된다.
- `version` 필수. 로드 시 버전별 마이그레이션 함수 체인(`v1→v2…`)을 적용하고, 알 수 없는 상위 버전·파싱 실패 시 덮어쓰지 않고 백업 키로 보관 후 새 세이브로 시작한다.
- 개인정보 없음. 크기 목표 < 50KB.
- 가져오기 파일은 신뢰할 수 없는 입력이다: 크기 상한, 스키마 검증, 알 수 없는 키(`__proto__` 등) 제거, 실패 시 기존 세이브 유지. 이 검증 테스트를 CI에서 돌린다.
- 내보내기/가져오기(JSON 파일)를 M2에 포함해 소실 위험(브라우저 데이터 삭제, 도메인 이전)을 완화한다.

### 인터페이스와 역할 분담
```ts
interface SaveStore {
  load(): Promise<SaveData | null>;
  save(d: SaveData): Promise<void>;
  clear(): Promise<void>;
}
```
- 처음부터 async로 둔다(localStorage는 동기지만, 나중에 원격 구현으로 바꿔도 호출부가 안 바뀐다). `Storage`를 주입받아 Node에서 DOM 없이 테스트한다.
- **Ben**: `SaveStore`, 마이그레이션, 검증 모듈 + 순수 TS 단위 테스트, 버전별 픽스처(`tests/fixtures/saves/v1.json`, CI에서 "구버전 → 최신 로드 성공" 검사). **Theo**: 게임 상태 연결, 체크포인트 저장 시점, 내보내기/가져오기 UI. 언어/빌드는 #4 ADR을 따른다.
- 작업량은 FE 연동 포함 약 3일로 본다(Theo 의견 반영).

## 반대 의견 (Dissent)
아직 없음. 가장 강한 반론: "나중에 통계가 필요해지면 늦다." 반박: 통계는 B로 추가 가능하고(아래), MVP 데모 단계에서는 소수 플레이테스트 피드백(수동)으로 충분하다. 반론이 현실화되면 재검토한다.

## 결과 (Consequences)
- 좋아짐: 0원, 단순함, 보안·개인정보 이슈 없음.
- 나빠짐: 기기 간 이동 불가, 소실 위험(내보내기로 완화), 통계 없음.
- 리스크: 세이브 스키마가 퍼즐 설계에 따라 변경됨 → `version`+마이그레이션 테스트로 대응.
- **나중에 서버를 붙일 때 바뀌는 범위**: `SaveStore`에 원격 구현체 추가, 익명 ID 발급 엔드포인트, 로컬↔원격 병합 규칙(`updatedAt` 최신 우선, 충돌 시 사용자 선택). 세이브 JSON 형식은 그대로 업로드 가능하므로 데이터 마이그레이션 불필요. B 이상은 비용 가능성이 있으면 L3로 올린다.
- **저장소 사용 불가 환경**: 쿠키 차단 시 `localStorage` 접근이 `SecurityError`, 용량 초과 시 `setItem`이 `QuotaExceededError`를 던진다. `SaveStore` 생성 시 쓰기를 한 번 시험(probe)하고, 실패하면 메모리 저장소로 대체하며 "이 브라우저에서는 진행 상황이 저장되지 않습니다" 안내를 띄운다. 예외로 부팅이 죽지 않아야 한다.
- **멀티 탭**: 두 탭에서 동시에 플레이하면 나중에 쓴 쪽이 이긴다(last-write-wins). MVP에서는 감수한다.
- **오리진 공유(Sam 지적)**: PR 프리뷰가 main과 같은 오리진이면 localStorage를 공유하므로, 프리뷰 빌드는 키 접두사에 빌드 ID를 붙이거나 별도 오리진을 쓴다. 배포 ADR(#5)에서 확정한다.
- 완화: 지원 브라우저에서 `navigator.storage.persist()`를 요청한다(효과는 브라우저별, 내보내기를 대체하지 않음).
- **ADR 번호**: 0005는 이슈 번호(#6)가 아니라 예약 번호다. 번호 규칙은 PM과 맞추고, 어긋나면 머지 시점에 재부여한다.
- 재검토 조건: 플레이테스트에서 기기 간 이동/통계 요구가 반복되거나 리더보드 기능이 기획될 때.
