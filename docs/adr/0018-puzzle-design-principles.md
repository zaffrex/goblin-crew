# ADR-0018: 퍼즐 설계 원칙: 능력 매트릭스, 상태와 시간, 공정성, 보송 게이지, 안정 ID

- 상태: 제안됨
- 날짜: 2026-11-15
- 작성자: **[디자이너 Luna]**
- 리뷰어: (요청) **[FE Theo]** 퍼즐 데이터 모델 ADR·BFS 검사와의 정합, **[BE Ben]** 안정 ID와 세이브, **[PM Noah]** 범위·승인
- 관련: 이슈 #18, ADR-0003(PR #15), ADR-0006, #7(아트), #10(SaveStore), 설계 회의 #1 스레드(#goblin-meeting). 화면 계획은 `docs/design/mvp-screen-matrix.md`

## 배경 (Context)
ADR-0003은 캐릭터 3명과 능력(`stretch / stomp / squeak`)을 정했지만, 퍼즐을 어떤 규칙으로 만들지는 "퍼즐 설계 원칙 문서"로 미뤘다. 그동안 리뷰와 회의에서 그 문서로 넘어온 항목이 다섯 역할에 흩어졌다.

- **Ben (설계 회의 #1 반대 담당)**: "화면 5개가 3인조로 버틴다는 근거가 예시 퍼즐 1개뿐이에요." stomp만 3번 쓰는 화면처럼 너무 쉬운 쪽 위험은 검증 수단이 없다. 상태 ID가 세이브에 들어가니 안정 ID 정책이 필요하다.
- **Noah (PR #15)**: 게이지 0 → `checkpoint` 리셋은 "실험을 벌주지 않는다"와 부딪힌다. PM 기본값은 위치만 리셋, 화면 진행 유지.
- **Theo (PR #15, 설계 회의 #1)**: 유지 상태 2개 제한은 BFS 한계가 아니라 인지 부하 기준이다(예시 퍼즐 약 1,700 상태). NPC도 시간 경과로 상태를 바꾸면 안 된다. 화면당 고유 프레임 반응에 하한을 두자.

Theo의 퍼즐 데이터 모델 ADR과 #7 프레임 예산이 이 숫자들을 기준으로 쓰인다. 그래서 M1 퍼즐 작업 전에 정해야 한다. CLAUDE.md 기준으로 퍼즐 설계 원칙은 L2다.

제약: MVP 화면은 3~5개다. 서버가 없고(ADR-0006) 자동 플레이 테스트는 headless로 돈다(ADR-0004). 아트 프레임이 가장 비싼 자원이다.

## 고려한 선택지 (Options)

### A. 숫자로 된 원칙 + 화면 매트릭스 문서 + BFS 자동 검사 (추천)
원칙을 검사할 수 있는 숫자로 쓰고, 화면 계획은 매트릭스로 관리한다. 지킬 수 있는 원칙은 데이터 모델 ADR의 BFS 검사로 CI에서 확인한다.
- 장점: Ben이 지적한 "너무 쉬운 화면"을 기계적으로 잡는다. 리뷰가 취향 싸움이 아니라 숫자 확인이 된다. 데이터 모델 ADR과 #7이 바로 이 숫자를 쓸 수 있다.
- 단점: 숫자가 창의적인 화면을 막을 수 있다. M1 플레이테스트 전이라 숫자 대부분이 추정치다.

### B. 문장으로 된 가이드라인만 두고 화면마다 판단
- 장점: 유연하다. 문서 비용이 적다.
- 단점: "능력 조합이 필요하다"를 화면마다 사람이 판단하면 Ben의 지적이 그대로 남는다. 데이터 모델 ADR이 검사할 기준도 생기지 않는다.

### C. M1 플레이테스트 뒤로 미루기
- 장점: 추정이 아니라 관찰로 정한다.
- 단점: M1 화면과 데이터 모델이 기준 없이 만들어진다. 게이지 리셋 범위처럼 엔진 구조에 닿는 결정은 나중에 바꾸기가 비싸다.

## 결정 (Decision)
**A를 채택한다.** 숫자는 모두 MVP용 시작값이다. M1 플레이테스트에서 관찰한 뒤 조정하고, 바꿀 때는 이 ADR을 대체하는 새 ADR을 쓴다.

### 1. 능력 사용 규칙 (매트릭스)
"필수"는 **그 능력을 쓸 수 없으면 그 화면을 풀 수 없다**는 뜻이다. 실패 반응에만 나오는 능력은 필수가 아니다.

| # | 규칙 | 검사 방법 |
|---|---|---|
| M1 | 모든 화면은 필수 능력이 2개 이상이다 (ADR-0003 규칙 1) | BFS: 능력 하나를 끄고 풀리면 그 능력은 필수가 아니다 |
| M2 | MVP 화면 중 1개 이상은 세 능력이 모두 필수다 (ADR-0003 규칙 1). 계획은 2개다 | 같은 검사 |
| M3 | 각 능력은 전체 화면의 절반 이상에서 필수다 (5화면이면 3화면 이상) | 매트릭스 집계 |
| M4 | 어떤 능력도 2화면 연속으로 필수에서 빠지지 않는다. 플레이어가 능력을 잊지 않게 한다 | 매트릭스 집계 |
| M5 | 한 화면의 **커밋된 정답 경로**(ADR-0004 결정 7의 `solution`)에서 능력 사용 중 한 능력이 차지하는 비율은 절반 이하다. 분모는 **능력 동사만** 센다(이동, 아이템 사용, 보기는 제외). Ben이 말한 "stomp만 3번 쓰는 화면"을 막는다 | `solution`의 동사 집계. 함께 BFS로 `solution` 길이가 최단 길이와 같은지 확인한다 |
| M6 | 최단 정답 경로 길이: 튜토리얼 화면 2~4 행동, 일반 화면 4~10 행동. 플레이어 입력 1번이 1행동이다(서는 자리로 이동하는 것도 1행동). **캐릭터 전환은 세지 않는다** | BFS 최단 경로 길이 |

- **매트릭스는 계획이고, 검증은 BFS가 한다.** 데이터 모델 ADR(Theo)에 "능력 1개를 끈 BFS", "`solution` 동사 집계", "`solution`이 최단인지 확인"을 넣는다. 매트릭스와 BFS 결과가 다르면 매트릭스를 고친다.
- **M5를 BFS 최단 경로가 아니라 `solution`으로 세는 이유**: 최단 경로는 보통 여러 개이고, BFS가 어느 것을 돌려줄지는 규칙 탐색 순서에 달려 있다. 그러면 데이터의 규칙 순서만 바꿔도 M5 결과가 바뀐다(Theo 리뷰). `solution`으로 세면 사람이 리뷰하는 경로와 CI가 세는 경로가 같아진다.
- **CI 판정 구분**: M1~M4, S3, I2는 **실패**(머지 막음)다. M5, M6, R1은 **경고**다. 경고로 둔 셋은 플레이테스트 전 추정치이고, 경고가 나면 PR에 이유를 적고 머지할 수 있다. M5를 경고로 두는 이유: 필수 능력이 2개인 화면은 "절반 이하"를 지키려면 두 능력을 정확히 같은 횟수로 써야 한다(stomp 2 + squeak 1이면 67%로 걸린다). "한 능력만 쓰는 화면"은 M1(필수 2개 이상)이 이미 실패로 잡는다.
- 화면 계획 초안: `docs/design/mvp-screen-matrix.md` (5화면, 능력별 필수 4화면, M1~M5 충족).

### 2. 상태와 시간
- **S1. 정지 상태, 시간 제한 없음** (ADR-0003 규칙 2를 그대로 따른다). 여기에 하나를 더한다. **NPC와 장치도 시간 경과로 상태를 바꾸지 않는다.** NPC의 대기 애니메이션(두리번거리기, 졸기)은 반복만 하고, 상태는 플레이어 행동으로만 바뀐다. 까치가 "몇 초 뒤 둥지로 돌아가면" 타이밍 퍼즐이 되기 때문이다(Theo 지적).
- **S2. 유지 상태는 화면당 2개 이하.** 유지 상태는 다른 캐릭터로 바꿔도 남는 능력 상태다(걸치기, 깔고 앉기, 매달리기). 근거는 **인지 부하**다. "지금 누가 뭘 붙잡고 있지?"를 플레이어가 기억해야 한다. BFS 한계가 아니다(Theo 계산: 예시 퍼즐 약 1,700 상태, 플래그 10개여도 약 22만). 유지 상태는 화면에서 항상 보여야 한다(그 캐릭터가 계속 그 자세로 그려진다). M1 플레이테스트로 조정한다.
- **S3. 막다른 상태 금지.** 도달할 수 있는 모든 상태에서 정답 상태로 가는 경로가 있어야 한다. 아이템 소모, 유지 상태 풀림, 아래 게이지 리셋 뒤 상태도 포함한다. BFS 검사로 확인한다(데이터 모델 ADR).
- **S4. 화면 클리어는 출구 플래그 하나로 정한다.** 한 명이 출구 조건을 만족하면 셋이 함께 다음 화면으로 가는 짧은 컷이 나온다. "셋 다 건너가기"를 퍼즐 조건으로 쓰지 않는다. 마지막 한 명을 옮기는 반복 작업은 재미가 없고 상태 수만 늘린다.

### 3. 공정성: 픽셀 헌팅 금지와 힌트
- **F1. 필수 핫스팟은 눈에 띈다.** 커서를 올리면(모바일은 탭하면) 이름이 뜬다. 필수 핫스팟은 배경과 명도 대비가 있어야 한다. 히트박스 최소 크기는 #7·UI 설계 문서 기준을 따른다.
- **F2. 실패 반응은 이유를 보여 준다.** "왜 안 되는지"가 보여야 다음 시도를 떠올린다. 예: 쭉이가 최대 길이에서 부들부들 떨다 되감기면 거리가 모자라다는 뜻이고, 삑이 협곡 중간에서 흩어지면 소리가 닿지 않는다는 뜻이다.
- **F3. 힌트는 2단계로 한다.** ① 화면에 들어가면 혼잣말 1개로 목표나 단서를 준다(`onEnter`). ② 같은 핫스팟에서 폴백 실패가 2번 나면, 그 캐릭터가 다른 캐릭터를 보며 "이건 내 일이 아닌가 봐" 같은 대사로 다른 능력을 암시한다. 이 카운터는 퍼즐 상태가 아니라 UI 상태다. 세이브와 BFS에 넣지 않는다. 힌트 버튼 같은 명시적 힌트 UI는 UI 설계 문서에서 따로 정한다.

### 4. 보송 게이지 (ADR-0003이 넘긴 항목)
- **G1. 5칸으로 시작한다.** 능력 사용은 무료이고, 다치는 실패만 1칸 줄어든다.
- **G2. 0이 되면 위치만 리셋한다 (PM 기본값 채택).** 셋이 축 늘어지는 "빨래 다시 해야겠다" 컷이 나온다. 그다음 게이지가 다시 찬다. ADR-0003의 "그 화면 시작 상태로 되돌아간다"를 아래처럼 구체화한다.
  - **리셋되는 것은 캐릭터 3명의 서는 자리뿐이다.** 셋 다 화면 시작 위치로 돌아간다.
  - **유지 상태는 모두 서는 자리로 모델링한다**(예: `at=hook`, `at=bush_top`, `at=canyon_bridge`). 그래서 위치를 리셋하면 유지 상태도 함께 풀린다. 유지 상태를 따로 플래그로 두지 않는다.
  - **NPC·장치 상태, 화면 진행 플래그, 얻은 아이템은 그대로 둔다**(예: `magpie.on_ground`는 리셋 뒤에도 유지).
  - 이렇게 하면 데이터에 플래그별 "리셋 여부" 속성이 필요 없다. S2 집계도 "유지 상태용 서는 자리에 캐릭터가 몇 명 있나"로 단순해진다.
  - 근거: 진행까지 리셋하면 다치는 실패가 웃음이 아니라 손해가 된다. 그러면 플레이어는 실패 리액션을 보려 하지 않는다. 우리 게임의 볼거리를 스스로 줄이는 셈이다.
  - 조건: 리셋 뒤 상태도 S3(막다른 상태 금지) 검사 대상이다. "진행 플래그 + 시작 위치" 조합이 막히지 않는지 BFS가 확인한다.
- **G3. 화면을 넘어가면 게이지를 가득 채운다(이월 없음).** 이월하면 앞 화면에서 많이 실험한 플레이어가 다음 화면에서 손해를 본다. MVP에는 회복 아이템을 두지 않는다.
- 이 규칙에서는 게이지가 벌이 아니라 **리듬**이다. 마구 누르는 행동을 컷 한 번으로 끊어 주고, 0이 되는 순간 자체가 개그다.

### 5. 반응 예산 (프레임 숫자는 #7에서 확정)
- **R1. 화면당 고유 애니메이션 반응은 4개 이상 12개 이하다.** 상한은 아트 비용 때문이고(#7 잠정: 1개당 4프레임 이하), 하한은 Theo 제안대로 모든 반응이 공용 리액션과 효과 조합처럼 보이지 않게 하려는 것이다.
- **R2. 나머지 반응은 조합으로 만든다.** 공용 실패 리액션(캐릭터당 4종: 넘어짐, 납작, 젖음, 찌릿), 엔진의 범용 효과 레이어(먼지, 별, 땀, "삑!" 글자, 흔들림), 대사를 조합한다.
- **R3. 대사는 말풍선 1개에 최대 2줄, 줄당 14자 이하다** (설계 회의 #1, ADR-0004 결정 3).
- **R4. 정답 단계의 반응은 반드시 고유 애니메이션이다.** 실패에는 공용 리액션을 써도 되지만, 성공 순간은 아끼지 않는다.

### 6. 안정 ID (Ben 요청)
- **I1. ID는 영어 소문자로 쓰고 의미를 담는다.** 예: `hanger_tower`, `magpie.on_ground`, `item.button_key`. 화면에 보이는 이름과 대사는 ID가 아니라 문자열 리소스로 관리한다. 대사를 고쳐도 ID는 바뀌지 않는다.
- **I2. 세이브에 들어가는 ID(화면, 상태 플래그, 아이템, 서는 자리)는 main에 머지된 뒤 이름을 바꾸지 않는다.** 꼭 바꿔야 하면 SaveStore 마이그레이션 별칭(#10)을 같은 PR에 넣는다. 사라진 ID 처리는 #10 완료 조건을 따른다.
- **I3. 규칙 ID도 같은 정책을 따른다.** 규칙 ID는 세이브에 들어가지 않지만, 자동 플레이 테스트와 "어떤 규칙이 발동했나" 로그가 참조한다.
- ID 문법(구분자, 네임스페이스)은 데이터 모델 ADR(Theo)이 정한다. 이 ADR은 "바꾸지 않는다"는 정책만 정한다.

## 반대 의견 (Dissent)
- **Theo (PR #21 리뷰, 반영함)**: "M5가 '최단 경로' 하나에 기대고 있어 결과가 정해지지 않아요." → M5를 커밋된 `solution` 기준으로 바꾸고 경고로 낮췄다. "G2에서 NPC·장치 상태가 리셋되는지 빠져 있어요." → "서는 자리만 리셋, 유지 상태도 서는 자리로 모델링"으로 적었다.

예상되는 다른 반론과 지금의 답:
- **"숫자 규칙이 재미있는 화면을 막는다"**: 예를 들어 한 능력만 집중해서 쓰는 개그 화면을 만들 수 없다. 답: MVP 5화면은 능력 조합을 가르치는 게 목적이라 이 제약이 맞다. 화면이 늘어나는 M2 이후에 M3~M5를 다시 본다.
- **"위치만 리셋하면 게이지가 의미 없다"** (G2): 맞는 지적이고 받아들인다. 게이지를 "벌"이 아니라 "리듬"으로 쓰는 것이 의도다. M1 플레이테스트에서 플레이어가 게이지를 아예 무시하면 진행 일부 리셋이나 실패 비용 조정을 다시 검토한다.
- **"힌트 2단계 카운터는 엔진 비용이다"** (F3): 핫스팟별 실패 횟수만 세면 된다. Theo 리뷰 결과 코어가 행동 결과에 `source`(rule / hotspotFallback / characterFallback)만 실어 주면 UI 카운터 30줄 안쪽이라 ②도 M1에 둔다. 대사는 캐릭터당 1~2종으로 제한한다. ①(`onEnter` 혼잣말)은 ADR-0003에서 이미 넘긴 항목이라 M1에 둔다.

## 결과 (Consequences)
- 좋아지는 것: 퍼즐 데이터 모델 ADR(Theo)이 검사할 항목(M1~M6, S3)이 정해진다. #7은 R1 숫자로 프레임 예산을 계산할 수 있다. Ben의 "화면 5개가 버티는가"에 매트릭스 초안으로 답하고, 이후에는 BFS가 계속 확인한다.
- 나빠지는 것: BFS 검사 항목이 늘어 데이터 모델과 CI 작업이 커진다(능력 끄기 3회 + `solution` 집계). Theo 추정으로는 화면당 그래프 순회 5번, 5화면 합쳐 CI 1초 안쪽, 검사 도구 구현 약 1일이라 크지 않다. 매트릭스와 실제 데이터를 맞추는 관리 비용, `solution`을 손으로 유지하는 비용이 생긴다.
- 새 리스크: 숫자가 추정치라 M1에서 많이 바뀔 수 있다. 특히 S2(유지 상태 2개)와 M6(경로 길이)가 그렇다. G2 때문에 게이지 긴장감이 약해질 수 있다.
- 다시 검토할 조건: M1 플레이테스트에서 (1) 플레이어가 유지 상태를 잊고 헤매거나, (2) 게이지를 무시하거나, (3) 힌트 ②가 너무 일찍 정답을 알려 준다는 관찰이 나오면 새 ADR로 숫자를 바꾼다. 화면이 6개 이상으로 늘어나는 시점에도 M3~M5를 다시 본다.
