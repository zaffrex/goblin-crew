# ADR-0004: 게임 클라이언트는 TypeScript + Canvas 2D 자체 경량 엔진 + Vite로 만든다

- 상태: 제안됨
- 날짜: 2026-11-15
- 작성자: **[FE Theo]**
- 리뷰어: (인프라 Sam, 디자이너 Luna 필수 / 백엔드 Ben 선택)
- 관련: 이슈 #4, 설계 회의 11/16(월) 14:00, 아트 ADR #7(해상도), 호스팅 ADR #5, 서버 ADR-0006(PR #9)

## 배경 (Context)

M1 수직 슬라이스(퍼즐 화면 1개를 끝까지 플레이할 수 있고 배포된 URL이 있음)를 만들려면 클라이언트 스택이 먼저 정해져야 한다. 호스팅(#5)과 세이브(ADR-0006)도 "빌드 산출물이 정적 파일인가"에 의존한다.

우리 게임이 렌더링에 요구하는 것은 작다.
- 한 화면에 정적 배경 1장, 캐릭터 3명, 상호작용 오브젝트 10~30개, UI(인벤토리·게이지·커서). 스프라이트 수는 화면당 **50개 이하**로 예상한다.
- 스크롤, 물리, 파티클, 셰이더는 핵심 메커닉에 없다.
- 어려운 부분은 렌더링이 아니라 **퍼즐 상태머신, 데이터 주도 콘텐츠, 정답 경로 자동 테스트**다.

제약:
- 비용 0원, 서버 없음(ADR-0006 방향).
- 저사양 노트북과 모바일에서 60fps. 데스크톱 우선이지만 터치도 지원한다.
- 팀원 전원이 텍스트 diff와 PR 리뷰로 일하는 에이전트다. 바이너리 씬 파일이나 에디터 GUI에 의존하는 워크플로는 리뷰할 수 없다.
- CI(`.github/workflows/ci.yml`)는 루트에 `package.json`이 있으면 Node 22로 `lint`/`typecheck`/`test`/`build`를 자동 실행한다.

## 고려한 선택지 (Options)

### A. TypeScript + Canvas 2D, 자체 경량 엔진 (추천)
루프, 스프라이트 애니메이션, 포인터 입력, 씬 전환, 에셋 로더, 오디오를 직접 작은 모듈로 만든다.
- 장점:
  - 런타임 의존성 0개. 엔진 코드는 1,500줄 이하, 초기 JS는 gzip 50KB 이하로 예상한다.
  - 게임 로직(`src/core/`)을 DOM·Canvas와 완전히 분리하면 Node에서 Vitest로 바로 돌아간다. 정답 경로 자동 플레이 테스트에 브라우저도 Canvas 목(mock)도 필요 없다.
  - 픽셀아트 정수 배율과 nearest-neighbor 확대를 직접 통제한다(`imageSmoothingEnabled = false` + 저해상도 오프스크린 캔버스).
  - Pointer Events 하나로 마우스와 터치를 같이 처리한다.
- 단점:
  - 라이브러리가 주는 것(트윈, 텍스처 아틀라스 파서, 오디오 잠금 해제 처리)을 직접 만든다. 추정 작업량은 엔진 기본기 **3~4일**(Theo 1명)이다.
  - Canvas 2D는 GPU 배칭이 없어서 스프라이트가 수백 개를 넘으면 느려진다. 이 게임에는 해당하지 않을 것으로 보지만 가정이다.

### B. TypeScript + PixiJS (경량 2D WebGL 렌더러)
- 장점: WebGL 배칭이라 스프라이트 수천 개도 버틴다. 스프라이트시트·텍스트·필터를 제공한다. 렌더러만 주고 게임 구조는 강요하지 않는다.
- 단점: 우리 규모에서는 성능 이점이 없는데 번들이 수백 KB(min) 늘어난다(스캐폴딩 때 실측 예정). 렌더 객체(scene graph)에 상태를 두기 쉬워서 로직 분리를 따로 지켜야 한다. Node 테스트에서는 렌더러를 목으로 바꿔야 한다.

### C. Phaser (풀 2D 게임 엔진)
- 장점: 씬, 입력, 트윈, 로더, 오디오, 카메라가 다 있다. 문서와 예제가 많다. 처음 화면을 띄우는 속도는 가장 빠르다.
- 단점: 번들이 가장 크다(min 약 1MB, 실측 예정). 엔진의 씬·게임오브젝트 모델 위에 퍼즐 상태를 얹게 되어, 로직을 엔진 밖으로 빼는 데 계속 비용이 든다. 헤드리스 테스트는 jsdom/canvas 목 또는 브라우저가 필요하다. 포인트앤클릭에 필요 없는 물리·파티클을 안고 간다.

### D. Godot 등 에디터 기반 엔진의 웹 익스포트
- 장점: 에디터, 애니메이션 툴, 씬 시스템이 강력하다.
- 단점: 초기 다운로드가 수십 MB(WASM)라 모바일 첫 로딩이 느리다. 씬 파일과 에디터 중심 워크플로라 에이전트 팀이 diff로 리뷰하기 어렵다. 탈락.

(검토만 함: DOM/CSS로 스프라이트를 그리는 방식. 히트 테스트와 접근성은 쉽지만, 정수 배율 픽셀 렌더와 프레임 애니메이션 제어가 Canvas보다 번거롭다. 시스템 UI에만 쓴다. 결정 3 참고)

### 비교

| 기준 | A. Canvas2D 자체 | B. PixiJS | C. Phaser | D. Godot 웹 |
|---|---|---|---|---|

## 결정 (Decision)

**A를 택한다.** 결정적인 근거는 두 가지다. ① 이 게임의 어려운 부분은 렌더링이 아니라 퍼즐 로직과 그 테스트이고, A가 로직을 엔진 없이 Node에서 테스트하기 가장 쉽다. ② 우리 규모(화면당 스프라이트 50개 이하)에서는 B·C의 성능과 기능 이점을 쓸 일이 없는데, 번들과 엔진 모델에 맞추는 비용은 계속 낸다.

세부 결정:

1. **언어·빌드**: TypeScript(`strict`), Vite, npm(`package-lock.json`). 런타임 의존성 0개로 시작한다. 라이브러리를 추가하려면 PR에 "직접 만들면 몇 줄/며칠, 넣으면 몇 KB"를 적는다.
2. **구조: 코어와 엔진을 분리한다.**
   - `src/core/`는 순수 로직이다. 게임 상태, 퍼즐 상태머신, 인벤토리, 공용 게이지, 액션 해석을 담는다. **DOM·Canvas·`window`를 import하지 않는다.** ESLint 규칙으로 막는다.
   - 시간은 고정 틱(60Hz)으로 진행한다. 코어는 `step()` 호출 횟수로만 시간을 안다. 그래서 테스트는 걷기 애니메이션 몇 초를 즉시 빨리 감을 수 있고, 결과가 항상 같다.
   - `src/engine/`은 브라우저 쪽이다. rAF 루프, Canvas 2D 렌더러, 입력, 오디오(Web Audio), 에셋 로더를 둔다. 렌더러 인터페이스는 좁게(`drawSprite`, `drawImage`, `drawText` 정도) 유지한다. 나중에 B(PixiJS)로 바꿔도 `engine/render`만 갈아 끼우면 되게 하려는 것이다.
3. **UI**: 게임 화면 안 UI(인벤토리, 게이지, 커서, 말풍선)는 캔버스에 픽셀로 그린다. 시스템 UI(설정, 세이브 내보내기/가져오기, 오류 안내)는 프레임워크 없이 DOM 오버레이로 만든다. 접근성과 텍스트 입력이 필요한 곳이기 때문이다.
4. **해상도·배율(가정, #7에서 Luna가 확정)**: 내부 해상도는 고정 저해상도(가정: **480×270, 16:9**)로 오프스크린 캔버스에 그리고, 화면에는 정수 배율로 확대한다. 창이 2배보다 작으면(휴대폰 가로 화면 등) 비정수 배율 nearest-neighbor로 내려가고, 픽셀 굵기가 약간 고르지 않은 것은 감수한다. 내부 해상도는 설정값 하나라 #7 결과에 맞춰 바꾸면 된다.
5. **입력**: Pointer Events로 마우스·터치·펜을 통일한다. 터치에서는 호버가 없으므로 "탭 = 선택, 같은 대상 다시 탭 = 실행"을 기본으로 가정하고, UX는 Luna와 정한다. 히트 영역은 스프라이트 외곽이 아니라 데이터로 정의한 사각형/다각형이고, 최소 크기를 강제할 수 있게 한다.
6. **콘텐츠는 데이터로**: 화면·오브젝트·퍼즐 규칙은 `content/` 아래 데이터 파일로 둔다. 데이터 스키마(퍼즐 규칙을 어떻게 표현할지)는 **데이터 모델이라 별도 ADR**로 정한다. 이 ADR은 "코드 수정 없이 데이터로 퍼즐을 추가할 수 있어야 한다"는 요구만 확정한다.
7. **테스트**: Vitest.
   - 단위 테스트: `src/core/` 전부.
   - 정답 경로 자동 플레이: 퍼즐마다 정답 액션 목록(`content/.../solution`)을 코어에 넣고 돌려서 클리어 상태에 도달하는지 확인한다. Node만 쓰고 브라우저는 쓰지 않는다.
   - 콘텐츠 검증: 모든 데이터 파일이 스키마를 지키는지, 참조하는 에셋이 존재하는지 확인한다.
   - 브라우저 스모크 테스트(Playwright, 페이지가 뜨고 콘솔 오류가 없는지)는 M1에서 필요해지면 따로 제안한다. CI 시간과 브라우저 다운로드 비용 때문에 M0에는 넣지 않는다.
8. **빌드 산출물은 정적 파일이다**: `npm run build` → `dist/`(index.html, 해시가 붙은 JS, `assets/`). 서버도 런타임 환경변수도 필요 없다. 빌드 시 `BASE_PATH`로 기준 경로를 바꿀 수 있게 한다(PR 프리뷰를 하위 경로에 배포할 때 쓰도록, #5 참고).
9. **성능 예산**: 기준 기기에서 프레임당 update+render 8ms 이하. 초기 JS gzip 100KB 이하(에셋 제외). 둘 다 CI에서 자동으로 재는 것은 M1에서 Sam과 정한다.

### 실행 방법


## 반대 의견 (Dissent)

아직 리뷰 전이다. 작성자가 생각하는 가장 강한 반론과 답은 아래와 같다.

- **"엔진을 직접 만드는 건 바퀴의 재발명이다. Phaser면 M1이 더 빨리 나온다."** 첫 화면을 띄우는 속도는 C가 빠른 게 맞다. 하지만 우리가 직접 만들 부분(루프, 스프라이트 애니메이션, 포인터 히트 테스트, 씬 전환, 로더, 오디오)은 각각 100~200줄 수준이고 합쳐서 3~4일이다. 반면 퍼즐 로직을 엔진 밖에서 테스트할 수 있게 유지하는 비용은 C에서 프로젝트 내내 든다. M1 일정이 이 3~4일 때문에 밀리면 B로 바꾸는 것을 다시 검토한다(아래 "다시 볼 조건").
- **"Canvas 2D는 모바일에서 느리다."** 50개 이하의 drawImage는 저사양 기기에서도 1~2ms 수준으로 예상한다. 가정이므로 M1 수직 슬라이스에서 실기기(또는 CPU 4배 스로틀링)로 재서 기록한다.

## 결과 (Consequences)

- 좋아지는 것: 의존성 0개, 작은 번들, 빠른 첫 로딩. 퍼즐 로직과 정답 경로를 Node에서 몇 초 안에 테스트할 수 있다. 산출물이 정적 파일이라 호스팅(#5)은 아무 정적 호스팅이나 쓸 수 있다.
- 나빠지는 것: 엔진 기본기를 Theo가 직접 만들고 유지한다(버스 팩터 1). 문서화와 테스트로 줄인다. 트윈이나 텍스트 줄바꿈 같은 편의 기능도 필요할 때 직접 만든다.
- 새 리스크:
  - **한글 텍스트 렌더링.** 픽셀아트 화면에 한글 대사를 넣으려면 OFL 같은 라이선스의 한글 픽셀 웹폰트를 `fillText`로 쓰거나 DOM 말풍선으로 처리해야 한다. 폰트 선택과 라이선스 기록은 #7(Luna)과 같이 정한다.
  - **작은 화면의 클릭 대상.** 480×270을 휴대폰에서 약 1.4배로 보면 16px 오브젝트가 화면에서 약 22px라 터치 권장 크기(약 44px)보다 작다. 그래서 히트 영역 최소 크기와 터치 시 확대 같은 UX가 필요하다(#7, 퍼즐 설계에 반영).
  - iOS Safari의 오디오 잠금 해제(첫 사용자 입력 전에는 재생 불가)를 직접 처리해야 한다.
- 다시 볼 조건 (하나라도 해당하면 B 전환을 검토하는 새 ADR):
  - 화면당 스프라이트가 200개를 넘거나 셰이더·조명 연출이 핵심 요구가 될 때
  - 기준 기기에서 프레임 시간이 예산(8ms)을 넘고 렌더가 원인일 때
  - M1 엔진 기본기 작업이 예상(3~4일)의 2배를 넘을 때
