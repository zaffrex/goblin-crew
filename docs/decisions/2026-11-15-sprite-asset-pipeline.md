# 결정: 스프라이트 원본은 `art/`, 출력 PNG·JSON은 `public/sprites/`에 커밋, 검사는 `npm test`

- 레벨: L1
- 날짜: 2026-11-15
- 결정자: 디자이너 Luna + 프론트엔드 Theo (PR 리뷰 승인으로 합의. ADR-0007 결정 7이 "M1 에셋 파이프라인 작업에서 Theo와 정한다"고 넘긴 항목)
- 참여: Luna(제안, 첫 시트), Theo(ADR-0007 PR #42 리뷰 초안: "원본은 `art/` 아래, 출력 PNG는 커밋, `npm test` 안에 팔레트 검사 + 다시 생성하면 diff가 생기는가 검사")
- 출처: ADR-0007 결정 4·5·7·8과 "후속 작업 (1)", 이슈 #113

## 배경
첫 실제 스프라이트(쭉이 서 있기 2 + 걷기 6)를 만들려면 원본을 어디 두고, 출력을 어디에 어떤 형식으로 두고, 무엇을 검사할지 정해야 한다. ADR-0007은 "텍스트 원본 + 인덱스 PNG 출력 + 팔레트 검사 + 시트 메타데이터"라는 요구만 정했다. 엔진이 시트를 읽기 시작하면 위치와 필드 이름을 바꾸기 비싸진다.

## 선택지
- A. **출력 PNG를 커밋하고, 검사에서 "다시 만들면 같은가"를 본다** (Theo 초안). 장점: 빌드에 그림 생성 단계가 없다. 리뷰어가 PR에서 PNG를 바로 본다. 원본과 출력이 어긋나면 테스트가 잡는다. 단점: PNG가 diff에 바이너리로 들어간다(시트 하나 약 2KB라 작다).
- B. 빌드 때 원본에서 PNG를 만든다(커밋하지 않음). 장점: 바이너리가 저장소에 없다. 단점: Vite 빌드에 생성 단계를 붙여야 한다. PR에서 그림을 보려면 직접 돌려야 한다.
- C. 원본만 그림 도구 파일로 둔다. 단점: ADR-0007 결정 7("원본은 텍스트")과 어긋난다.

## 결정
**A로 한다.**
1. **원본**: `art/` 아래 텍스트(스크립트). 공용 그리기 도구는 `art/lib/pixel.mjs`, 캐릭터별 포즈는 `art/sprites/<캐릭터>.mjs`, 생성 진입점은 `node art/build.mjs`.
2. **출력**: `public/sprites/<시트>.png` + `public/sprites/<시트>.json`. Vite가 `public/`을 그대로 `dist/`로 복사한다. 엔진은 `assetUrl('sprites/<시트>.json')`으로 읽는다(ADR-0004 결정 8).
3. **PNG 형식**: 8비트 인덱스 PNG. 색 인덱스 0~31 = 보송 팔레트 인덱스 그대로. 투명은 32번 + `tRNS`. 팔레트 원본은 `docs/design/art/bosong-32.hex` 한 파일이다.
4. **시트 배치**: 가로 한 줄. 프레임 번호 = 왼쪽부터 칸 순서.
5. **메타데이터 필드**(좌표는 칸 왼쪽 위 기준 px):
   - `cell: [w, h]` 칸 크기(16의 배수)
   - `anchor: [ax, ay]` 기준점. `ax` = 서 있기 0번의 두 발 가운데(두 발 폭 짝수), `ay` = 칸 높이. 왼쪽을 볼 때는 `ax` 경계를 축으로 뒤집는다.
   - `hit: [x, y, w, h]` 히트 영역 기본값 = 서 있기 0번 그림 박스(도구 포함)
     - (개정 2026-11-16, #203) 손 기준점(`hand`)이 있는 매달린 자세는 anim에 자기 `hit: [x, y, w, h]`(그 자세 모든 칸 그림 박스의 합집합, 오른쪽을 본 시트 기준)를 생성 스크립트가 적는다. 엔진은 그 자세를 그리는 동안 이 값으로 클릭 상자를 만든다(그리는 위치·방향 규칙 그대로). 폭·높이는 24 이상이다. 생성 스크립트의 고리 손 기준점 검사도 `hold`만이 아니라 `hand` 있는 모든 자세를 본다.
   - `head: [x, y, w, h]` UI 초상화용 머리 박스(24×24로 자른다)
   - `walkCycle` 걸음 주기 px. 걷기 프레임 = `floor(걸은 거리 / (walkCycle / 6)) % 6`
   - `anims: { 이름: { frames: [...], ms: [...] } | { frames: [...], by: "distance" } }`. `ms`는 50ms 배수.
   - `anims` 키(엔진 연결 #140에서 정함): `idle`(서 있기, 반복), `walk`(거리 넘김), `hold`(유지 자리 매달림, 반복), 그리고 화면 데이터 `anim` 이벤트 이름 그대로(`common.bump_bottom` 등, 한 번 재생 후 마지막 장 유지). 마지막 장은 그 캐릭터의 다음 `walk`·`release`·`place`·`anim`, 기절, 또는 재생할 이벤트가 다 끝날 때(busy 끝)까지 유지한다(#189). 매달림(`hold`)은 퍼즐 상태가 아니라 몸이 `hold` 자리 점에 놓였는지로 정한다(퍼즐 상태는 연출 전에 바뀐다). 시트에 없는 키는 엔진이 임시 실루엣으로 그린다. 시트는 `public/sprites/<캐릭터>-base.json`을 빌드 때 모으므로 json·png만 넣으면 붙는다.
   - 프레임별 덮어쓰기(`anchor`)와 장대 포즈의 `grip`은 그 프레임이 처음 생기는 시트(쭉이 리액션 시트)에서 `frames` 배열로 더한다. 지금은 넣지 않는다.
   - 5-1. **칸 위로 나가는 장대**(개정 2026-11-16, #142, `#goblin-dev` 11/16 Theo 초안 → Luna 합의). 화면 1 `reach_hang_up`처럼 장대가 칸(48×64) 밖까지 뻗는 자세에만 쓴다.
     - anim에 `tip: [[x, y], ...]`(프레임마다, 칸 안에서 장대가 나가는 점 = 0행 장대 픽셀 가운데)과 `claw: [n, ...]`(프레임마다 집게 칸 번호). 좌표는 `hand`처럼 오른쪽을 본 시트 기준이다.
     - 시트 최상위 `claw: { image, cell, anchor }`: 집게 칸 줄(`<시트>-claw.png`, 8×8, 0 벌림 / 1 다묾). `anchor` (4,8) = 장대가 들어오는 아래 가운데.
     - 엔진(개정 2026-11-16, #189): `tip`과 집게 `anchor`는 시트 `anchor`처럼 **픽셀 경계(연속 좌표)**다. 장대는 직선(ADR-0003)이라 tip x에서 **수직으로** 그 행동 대상(핫스팟 `reachPoint`)의 **y까지만** 잇는다(대상 x는 쓰지 않는다. 2px 장대를 뒤집으면 가운데선이 1px 옮겨 가서 대상 x로 꺾으면 꺾임이 생긴다, PR #188 리뷰). 이은 장대는 그 프레임 **tip 행의 4px(장대 2px + 양옆 잉크)를 위로 늘려** 붙인다. 시트 장대와 이음매가 없다. **마디(개정 2026-11-17, #194)**: ADR-0007 장대 3조각대로 마디 이음매는 **8px 주기**다. 시트는 모든 자세에서 장대 위 끝(집게가 붙는 점) 8px 아래부터 8px마다 한 행을 마디로 칠한다(장대 2px를 dusk로, `#dd#`). tip 자세는 메타 anim에 프레임마다 `joint`(tip 행부터 아래로 첫 마디 행까지 px, 0~7)를 적고, 엔진은 이은 구간에서 `tip 행 + joint − 8m`(m ≥ 1, 대상 y 이상) 행마다 시트의 그 마디 행 4px를 1행씩 덮어 붙인다. 그래서 시트 장대와 이은 장대의 마디 무늬가 한 줄로 이어진다. `art/build.mjs`는 그 행이 손 등에 가리지 않은 순수 마디 행(잉크·dusk·dusk·잉크)인지 검사한다. `joint`가 없으면 마디 없이 늘인다. 끝에 `claw` 칸을 `anchor`가 (tip x, 대상 y)에 오게 그린다. 왼쪽을 보면 장대·집게를 tip x 축으로 같이 뒤집는다. 대상 점이 칸 위가 아니거나 대상에 `reachPoint`가 없으면 잇지 않는다.
     - 연출 anim에 `facing`이 있으면 그 연출 동안 그 방향이다(`hold.facing`보다 앞선다, #189). `reach_hang_up`은 퍼즐 상태가 이미 바닥으로 바뀐 뒤 고리에서 재생되기 때문이다.
     - **늘어나기와 모자람(개정 2026-11-18, #284)**. 사장님 판정 2 2차에서 "특기가 발동 안 됨"으로 읽힌 원인 중 하나가 장대가 대상 쪽으로 안 늘어나는 것이었다.
       - 시트 `claw.max`(px): 칸 위로 늘어나는 최대 길이. `claw.growMs`(ms): 연출 시작부터 다 늘어날 때까지. 그 사이 길이는 시간에 비례한다(첫 틱은 칸 위 끝에 집게만). 둘 다 없으면 예전처럼 첫 장부터 대상까지 다 잇는다. 쭉이는 `max` 64(고리 → 둥지 62px는 닿는다), `growMs` 300.
       - anim `short`(px, 실패 연출): 장대 끝(집게 기준점)이 대상 점보다 이만큼 아래에서 멈춘다. 쭉이 `common.reach_wobble`은 10(집게 8px + 2px 틈).
       - 길이 = min(대상 점 y − `short`, `max`) × 늘어난 비율. 대상 점은 핫스팟 `reachPoint`, 없으면 **대상 상자 아래 끝 가운데**(고리처럼 `reachPoint` 없는 자리). 대상도 상자도 없으면 `max`까지, `max`도 없으면 잇지 않는다. 대상 점이 칸 위가 아니면 잇지 않는다.
       - 칸마다 `tip`이 `null`일 수 있다(그 칸은 잇지 않는다, `claw`·`joint`도 `null`). 첫 칸은 `null`이 아니다(연출 시작부터 늘인다). 쭉이 `reach_wobble` 3번 칸(장대가 넘어와 정수리를 침)이 그렇다.
       - 그래서 바닥에서 둥지에 `のばす`를 쓰면 장대가 0.3초 동안 위로 늘다가 둥지 한참 아래(최대 길이)에서 휘청이고, 고리에 쓰면 집게가 고리 상자 바로 아래에서 멈춘다(화면 1 설계 9번 "팅").
     - 생성 스크립트 검사: `tip`이 한 프레임이라도 있으면 첫 칸에 있고, tip 있는 칸마다 `claw` 번호가 집게 칸 수 안이고 마디 행이 순수하다. anim `short`는 0 이상 정수다.
   - 5-2. **칸 신호 `cue`**(개정 2026-11-16, #199 L1 PM, PR #198 Theo 리뷰). 연출의 "박자" 칸에 맞춰 글자·효과를 띄울 때 쓴다(삑삑이 `common.squeeze_chicken`: "삑!"이 흐익 칸 뒤가 아니라 꽉! 칸에).
     - `ms` 자세에 `cue: n`(이 연출 `frames`의 n번째 칸, 0부터). 거리 넘김 자세(`walk`)에는 둘 수 없다. 이름 없는 숫자 하나뿐이다. **시트는 fx 이름을 모른다**: 무엇을 띄울지는 화면 데이터 show가, 언제인지만 시트가 정한다(글자를 바꿔도 그림을 다시 빌드하지 않는다).
     - 엔진(`scene.ts`): 캐릭터 연출이 `cue` 칸에 닿으면(앞 칸들 `ms` 합, 틱 올림) show에서 그 연출 **바로 뒤의 `fx` 하나**를 그때 띄운다(신호 하나 = fx 하나). 연출과 겹쳐 따로 시간이 가고(`overlays`), 남아 있는 동안 busy다. 그 뒤의 fx는 지금처럼 연출이 끝난 뒤 차례로 뜬다(둥지 삑: 메아리 `small_squeak_text`는 원래 "삑!"보다 늦게 와야 메아리로 읽힌다, ADR-0003, PR #201 Luna 리뷰). 바로 뒤가 `fx`가 아니면 신호는 아무것도 띄우지 않는다. 연출 길이와 다음 이벤트 시작 시각은 바뀌지 않는다. 화면 데이터 형식·`step`(코어)은 바뀌지 않는다.
     - 시트·자세·`cue`가 없으면(실루엣, 옛 시트) 지금처럼 연출이 끝난 뒤 fx가 차례로 뜬다.
     - 생성 스크립트 검사: `cue`는 그 자세 칸 수 안의 정수다. `parseSpriteMeta`도 같은 검사를 하고, 틀리면 그 캐릭터는 실루엣이다.
     - **개정 2026-11-18 (#284, [ability-feedback](2026-11-18-ability-feedback.md) L1)**: `cue`는 숫자 또는 **오름차순 숫자 배열**이다. k번째 신호는 연출 바로 뒤에 이어진 fx 중 k번째를 띄운다(쭉이 `common.reach_wobble` `[0, 1]`: `ビヨーン` → 고리 `キン`). 이어진 fx가 신호보다 적으면 남는 신호는 아무것도 띄우지 않는다. 숫자 하나는 `[n]`과 같다. 검사는 배열이 비지 않고, 칸 수 안이고, 엄격히 오름차순인지까지 본다.
     - 한계: 한 연출에 신호는 하나, 신호가 띄우는 fx도 하나다. 두 fx를 같은 칸에 띄우거나 칸마다 다른 fx가 필요해지면(예: 쿵 먼지 + 소리 글자를 다른 칸에) 그때 이름 붙은 신호로 넓힌다.
   - 5-3. **앞 칸 다시 쓰기 `reuse`**(개정 2026-11-19, #414 L1, PR #417 Theo 리뷰 → `magpie_nest.md` 1-6-3절). 새 픽셀 없이 이미 그린 칸을 이어 새 연출을 만들 때 쓴다(묵직이 `seesaw_stomp`).
     - 시트 원본 자세에 `frames` 대신 `reuse: [[자세 이름, 칸 순서], ...]`. 전체 칸 번호로 적으면 시트에 칸을 넣을 때 밀려서 이름으로 가리킨다. 가리키는 자세는 원본 `anims`에서 **앞에** 있어야 한다. `ms`는 칸 수와 길이가 같다. 거리 넘김 자세에는 못 쓴다.
     - 산출 메타는 지금처럼 `frames: number[]`이고, 그 번호가 다른 자세와 겹칠 수 있다(시트 이미지에 칸이 늘지 않는다). 검사(`tests/art/sprites.test.ts`)는 "칸 번호가 겹치지 않는다" 대신 "쓰인 칸 번호가 0부터 빈틈없이 이미지 칸 수와 같다"를 본다.
   - 5-4. **공중 칸 `air`**(개정 2026-11-19, #414 L1). 엔진이 몸을 궤적 위에 놓는 칸이다.
     - `ms` 자세에 `air: [첫, 끝]`(칸 순서). 끝 다음 칸이 **착지 칸**이라 끝 < 칸 수 − 1이다. 높이(H)는 시트가 아니라 엔진 상수(`scene.ts` `HOP`)다.
     - 엔진: 이 자세가 `board` 자리(판 끝)를 대상으로 재생되면 `air` 앞 칸은 웅크림, `air` 칸은 공중(x 직선 + y 포물선), 착지 칸이 시작되는 틱에 그 이벤트가 끝나 대기열이 다음 이벤트로 넘어간다. 남은 칸과 ⑦ 내려서기는 대기열 밖 깡충으로 돌고 busy다. 시트·`air`가 없으면 지금처럼 그 자리에서 끝까지 재생한다.
     - 생성 스크립트와 `parseSpriteMeta`가 같은 검사를 한다(틀리면 그 캐릭터는 실루엣).
6. **검사**(`tests/art/sprites.test.ts`, `npm test`): 다시 만들면 바이트가 같다 / 인덱스 PNG이고 팔레트는 보송 32색(+ 투명)뿐 / 칸·이미지 크기·기준점·박스 범위 / 걷기 6장·거리 넘김 / 캐릭터 시트 합계 300KB 경고선. 생성 스크립트는 "두 발 폭 홀수", "딛은 발이 바닥 행에 안 닿음"이면 오류를 낸다.

## 반대 의견
