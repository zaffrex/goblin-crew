# 결정: 화면 배경·물건 그림 형식 v1 (배경 한 장 + 물건 시트, 멈춘 모습은 `when`, 움직임은 `anim`)

- 레벨: L1
- 날짜: 2026-11-16
- 결정자: 프론트엔드 Theo + 디자이너 Luna (#157 제안·답으로 합의)
- 참여: Theo(제안 v1, Q1~Q3), Luna(Q1~Q3 답, 필수 추가 A·B·C와 `loop`)
- 출처: 이슈 #157 본문·코멘트, #145 본문 "형식(배경 한 장 + 물건 시트, 상태별 그림)은 Theo와 정한다", ADR-0007 결정 2·3·8, `docs/design/screens/magpie_nest.md` 1-1~1-4절, [스프라이트 파이프라인 기록](2026-11-15-sprite-asset-pipeline.md)

## 배경
화면 1 배경(#145)이 완성 밀도 샘플(#154)로 사장님 OK를 받았고, Luna가 물건 시트 ③을 그리기 전에 엔진이 읽을 형식을 맞춰야 다시 그리는 일이 없다. ADR-0007 결정 8은 "필드 이름과 파일 형식은 M1 에셋 파이프라인 L1에서 Theo와 정한다"고 넘겼다. 캐릭터 시트 형식은 이미 정했으니(위 기록), 여기서는 **화면 배경과 만질 수 있는 물건**만 정한다.

## 선택지
- A. **배경 한 장 + 물건 시트. 물건은 화면에 제자리로 그리고 빌드가 잘라서 좌표를 넣는다** (Theo 제안). 장점: 그림이 `magpie_nest.json` 좌표를 벗어날 수 없다. 호버 외곽선(ADR-0007 결정 2)을 물건마다 만들 수 있다. 단점: 빌드 스크립트가 자르기·검사를 맡아 커진다.
- B. 배경에 물건까지 다 구워 넣고, 바뀌는 것만 덮어 그린다. 장점: 파일 하나, 빌드 단순. 단점: 투명 경계가 없어 호버 외곽선을 못 만든다. 까치처럼 자리가 바뀌면 배경 쪽 그림을 지울 수 없다. 캐릭터와 앞뒤를 못 정한다.
- C. 물건 시트를 캐릭터 시트처럼 칸 단위로 그리고 좌표를 사람이 적는다. 장점: 캐릭터 시트와 형식이 같다. 단점: 좌표를 두 곳(화면 JSON, 시트)에 적어 어긋날 수 있다. Luna가 칸마다 위치를 계산해야 한다.

## 결정
**A로 한다.** #157 제안에 Luna의 추가 A·B·C와 `loop`를 넣은 것이 v1이다.

### 1. 파일
- 원본: `art/scenes/<화면>.mjs` (지금 `docs/design/screens/magpie_nest-density-sample.mjs`의 그리기 코드를 옮긴다). 질감 붓은 `art/lib/`를 쓴다.
- 출력(`node art/build.mjs`, 커밋): `public/scenes/<화면>-bg.png`(480×270, 불투명 인덱스 PNG), `public/scenes/<화면>-objects.png` + `.json`.
- PNG 형식·팔레트·"다시 만들면 바이트가 같다" 검사는 캐릭터 시트와 같다.

### 2. 배경에는 만질 수 없는 것만
`magpie_nest.json`에서 `box`가 있는 대상(hotspot `magpie`·`nest`·`basket`·`long_johns`, spot `seesaw_left`·`seesaw_right`·`hook`)은 모두 물건 시트로 뺀다. 빨랫대 기둥, 빨랫줄 기둥, 담장, 수건, **시소 받침(세제 통)** 은 배경이다.

### 3. 그리는 쪽은 좌표를 적지 않는다
`.mjs`에서 물건의 그림마다 **480×270 투명 화면에 제자리로** 그린다. 빌드가 불투명 영역을 잘라 시트에 붙이고 `at`(화면 좌표, 왼쪽 위)을 넣는다.

```js
// art/scenes/magpie_nest.mjs (모양)
export const SCENE = {
  id: 'magpie_nest',
  bg(img) { /* 480×270 */ },
  objects: {                                   // 적은 순서 = 뒤 → 앞 (같은 층 안에서)
    nest: {
      draw(img) {},                            // default: 열쇠 있음
      loop: { ms: [1600, 120, 120], frames: [(img) => {}, (img) => {}, (img) => {}] }, // default의 반복(반짝임)
      states: [{ when: { flags: { 'nest.key_taken': true } }, draw(img) {} }],
    },
    magpie: {
      draw(img) {},                            // 둥지 위, 캐릭터 뒤
      loop: { ms: [2500, 150, 300], frames: [/* U8 */] },
      states: [{ when: { flags: { 'magpie.on_ground': true } }, layer: 'front', draw(img) {}, loop: { /* U8 바닥 */ } }],
    },
    long_johns: { draw(img) {} },
    seesaw: { ids: ['seesaw_left', 'seesaw_right'], draw(img) {} }, // 널빤지 한 장, ID 둘
    basket: {
      draw(img) {},                            // 뒤판 + 안쪽
      overlay: { sortY: 236, draw(img) {} },   // 앞판(높이 10px)
    },
    hook: { draw(img) {} },
  },
  anims: {
    'seesaw_right.plank_bounce': { ms: 80, frames: [/* 3장: 오른쪽이 내려감 */] },
    'seesaw_left.plank_bounce': { ms: 80, frames: [/* 3장: 왼쪽이 내려감 */] },
    'magpie.fly_down': { ms: 100, frames: [], layer: 'front' },
  },
};
```

### 4. 멈춘 모습은 상태에서, 움직임은 이벤트에서
- **멈춘 모습**: `when`이 맞는 첫 state, 없으면 `default`. `when` 문법과 "첫 일치"는 핫스팟 `variants`와 같다(`src/core/interact.ts` `hotspotBox`).
- **반복(`loop`)**: state·`default`에 선택 필드 `loop: { ms: number | number[], frames }`. `ms`가 배열이면 프레임별 시간이다(길게 멈췄다 짧게 움직이는 반짝임·U8 까치 대기). 시계는 화면 전체가 하나라 반복끼리 박자가 맞지 않아도 된다. `loop`가 없으면 그림 1장이다.
- **일시 연출(`anim`)**: 이벤트 `[대상, 이름]`이 오면 `anims["대상.이름"]`을 한 번 재생하고 멈춘 모습으로 돌아간다. 시트에 없으면 건너뛴다. 대상이 `@서는자리`(그 자리에 선 캐릭터)인 이벤트는 캐릭터 시트 몫이라 화면 시트는 보지 않는다.
- **`ms`는 정수 ms**다. 캐릭터 시트의 "50ms 배수" 규칙은 화면 시트에 두지 않는다(반짝임 120ms 같은 짧은 깜빡임이 필요하다). 렌더는 이미 rAF로 매 프레임 돌므로(`src/engine/loop.ts`) `loop` 추가 비용은 프레임 고르기 함수 하나다.
- **busy 길이**: 화면 시트에 있는 anim은 그 길이(ms 합을 60Hz 틱으로 올림)가 그 이벤트의 busy 길이가 된다. 없으면 지금처럼 `TIMING.anim`(30틱)이다. 그래서 Luna가 프레임 시간을 정하면 연출 박자가 그대로 따라간다.
- ADR-0065 "엔진은 `events`로만 반응한다"와의 관계: **반응(연출)은 이벤트로만** 한다. 멈춘 모습은 추측이 아니라 데이터(`when`)가 정한 것이고 히트 박스 `variants`와 같은 규칙이다. 이렇게 해야 게이지 0 리셋 뒤(A3, 까치가 바닥에 남음)와 M2 세이브 로드 뒤 화면이 맞는다. ADR 문장을 바꾸지 않고 해석을 기록하는 것이라 L1이다.

### 5. 물건 하나, ID 여럿 (`ids`)
- `ids`가 있으면 그 물건이 여러 대상을 맡는다. 없으면 키가 곧 ID다. 시소는 `seesaw = { ids: ['seesaw_left', 'seesaw_right'] }`로 널빤지 한 장이다(설계 3절 "시소 두 끝은 한 물건").
- `ids`에 있는 대상으로 오는 anim(`seesaw_left.plank_bounce`, `seesaw_right.plank_bounce`)은 이 물건을 바꿔 그린다. 방향이 반대라 2개를 따로 그린다.
- 판정(히트 박스)은 지금처럼 spot별 상자다. 호버 외곽선은 널빤지 전체가 켜지고, 어느 끝인지는 커서 라벨이 알린다.
- Q1 답: 시소는 사람이 서 있어도 **수평 고정**이다(설계 1-3절). 기울기는 `plank_bounce` 안에서만 보인다.

### 6. 앞뒤 순서 (설계 1-4절)
그리는 순서는 다음과 같다.
1. 배경 → `layer: 'back'`(기본) 물건을 `objects`에 적은 순서로
2. 캐릭터와 `overlay`(`sortY` 있는 조각)를 **발 y 순서**로 섞어서. 발 y가 `sortY` 이하인 캐릭터는 조각 뒤, 큰 캐릭터는 앞이다. 바구니 앞판(`sortY` 236 = 바구니 바닥)이 바구니 **안** 캐릭터만 가리고, 바구니 앞을 지나가는 캐릭터(발 y 244)는 가리지 않는다.
3. 고리에 매달린 캐릭터(항상 캐릭터 맨 앞)
4. `layer: 'front'` 물건 → 효과 레이어 → 말풍선(DOM)

- `layer`는 물건이 아니라 **state·`default`·anim 단위**다(Luna B). 둥지 위 까치는 뒤, 바닥의 까치(state)와 `fly_down`은 캐릭터 앞이다. 까치가 쭉이를 노려보는 장면에서 다리에 가리면 안 되기 때문이다.
- #157 제안의 `front: true` + `back()` 나눔은 이것으로 바꾼다. 바구니 앞판을 "모든 캐릭터 앞"에 두면 바구니 앞을 지나는 캐릭터의 다리가 가려진다.
- y 정렬은 `overlay` 조각에만 한다. 물건끼리는 적은 순서다.

### 7. 고리 손 기준점 (Q3)
- 고리(`hook`)는 물건이다. 매달린 캐릭터는 지금처럼 발 (160,160)에 세우고, 매달린 자세(`hold`) 프레임의 손 위치가 **(158,100)** 에 오게 그린다(설계 1-2절 "발 160,160 / 손 158,100").
- 이 값은 `art/scenes/magpie_nest.mjs`의 `grips: { hook: [158, 100] }`에 둔다. 캐릭터 시트에 `hold` 프레임별 `hand`가 생기는 PR에서 "발 + (hand − anchor) = grip"을 검사한다. 지금 화면 JSON(`src/core/puzzle/` 타입)은 바꾸지 않는다.

### 8. 빌드 검사 (`npm test` 실패)
- 배경은 480×270이고 **0번 ink·31번 hint 픽셀이 없다**(ADR-0007 결정 3-1을 스크립트로 확인).
- 배경 PNG 100KB 이하(ADR-0007 결정 8).
- `objects` 키 또는 `ids` 항목은 화면 JSON의 hotspot·spot ID다. 한 ID를 두 물건이 맡지 않는다.
- `when`의 플래그는 화면 JSON `flags`에 있다. `anims` 키의 대상은 어떤 물건의 ID다.
- 그림의 불투명 영역은 **그 상태의 히트 박스와 겹친다**(`ids`면 상자 중 하나 이상). 까치 바닥 그림이면 `variants`의 `[88,212,24,24]`다.
- `loop`·anim의 `ms`는 양의 정수이고, 배열이면 `frames`와 길이가 같다.

### 9. 폴백
배경 PNG가 없으면 지금 `drawRoom`, 시트에 없는 대상은 지금 `drawTargets` 상자로 그린다. 띠 하나·물건 하나씩 붙여도 배포본이 깨지지 않는다.

### 10. 구현 순서 (#157)
1. `art/build.mjs` 화면 빌드 + 8번 검사(장면이 비어 있어도 돈다)
2. `src/core/sceneArt.ts` 순수 함수(상태 → 물건별 그림, anim·loop 프레임, busy 길이) + 테스트, `src/engine/sceneArt.ts` 로더·그리기, `main.ts` 연결과 폴백
3. 물건 호버 외곽선(ADR-0007 결정 2). 판정 2 전에 넣을지는 PM이 정한다.

## 반대 의견
- Luna(Q1): 수평 고정 널빤지는 "무게로 튕긴다"를 덜 알린다. → L24·L22 대사가 맡고, 그림으로 따로 보충하지 않는다.
- Luna(Q2) 비용 우려: `loop` 때문에 화면이 계속 다시 그려져야 한다. → 엔진은 이미 rAF로 매 프레임 그린다. 추가 비용은 프레임 고르기뿐이라 받아들였다.
- Theo: anim 길이를 busy로 쓰면 그림 PR이 연출 박자(재생 도구 `replay.ts` 대기 시간)를 바꾼다. → 재생 도구는 busy가 끝나기를 기다리는 방식이라 영향이 없다. 길이가 너무 긴 anim은 리뷰에서 본다.
- 가장 강한 반론: "`overlay`+`sortY`는 바구니 하나 때문에 만든 장치다." → 화면 2부터 앞뒤가 필요한 물건(문틀, 담장 구멍)이 생기면 같은 장치를 쓴다. 안 생기면 M2 회고에서 지운다.

## 다시 볼 조건
- 앞뒤가 `layer`·`overlay`로 안 풀리는 물건이 나오면(예: 캐릭터가 물건을 돌아 걷는 화면) → y 정렬 일반화
- 화면 시트 하나가 100KB를 넘거나 물건이 20개를 넘으면 → 화면별 시트 분할
- 세이브 로드(M2)에서 멈춘 모습이 `when`만으로 복원되지 않는 경우가 나오면 → ADR-0065 개정 검토(L2)
