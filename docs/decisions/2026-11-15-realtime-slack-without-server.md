# 결정: 서버 없이 Actions 리스너로 Slack에 준실시간 반응한다

- 레벨: L3(사장님)
- 날짜: 2026-11-15
- 결정자: 사장님 (요청), 구현 방식은 셋업 담당 Claude가 제안
- 참여: 사장님, 셋업 담당 Claude. 운영 검토는 인프라 Sam과 백엔드 Ben에게 넘김
- 출처: 사장님 요청 "모두들 바로바로 대답도 하게 해주고 서로 활발하게 커뮤니케이션 하면서 일을 진행하게 해줘. 서버가 정말 필요하다면 검토해줘"

## 배경
에이전트는 매시간 정기 작업과 GitHub 이벤트로만 깨어났다. 그래서 Slack에서 사장님이나 동료가 불러도 답이 최대 1시간 걸렸고, 멤버끼리 묻고 답하는 대화가 이어지지 않았다.

## 선택지
- A. **Actions 폴링 리스너** (`slack-listener.yml`): 긴 Actions 잡이 15초마다 팀 채널과 사장님 DM을 읽고, 멘션된 역할을 `agent.yml`로 깨운다.
  - 장점: 비용 0원(public 저장소), 새 계정이나 Slack 앱 재설정 없음, 바로 적용
  - 단점: 반응까지 약 2~4분(폴링 15초 + 에이전트 기동), 잡 교대 시 몇십 초 공백, Actions를 상시 프로세스처럼 쓰는 방식이라 GitHub 정책 변화에 취약
- B. **Slack Socket Mode 상시 프로세스**: 진짜 실시간 이벤트
  - 단점: 상시 켜진 머신이 필요(서버). 앱마다 app-level 토큰과 이벤트 구독을 추가해야 해서 Slack 관리자 작업이 다시 필요
- C. **서버리스 Events API** (Cloudflare Workers 등 무료 티어 → GitHub `workflow_dispatch`)
  - 장점: 실시간에 가깝고 무료 티어로 충분
  - 단점: 외부 서비스 계정(사장님 소유)과 공개 엔드포인트가 생김. Slack 앱 5개에 이벤트 구독 설정 필요
- D. 유료 상시 서버(VPS)
  - 단점: 월 비용(L3), 운영 부담

## 결정
A로 시작한다. 지금의 병목은 "1시간 대기"였고, 2~4분 반응이면 대화가 이어지기에 충분하다. 서버(B, D)는 아직 필요 없다.
에이전트 기동에 걸리는 1~2분은 서버를 둬도 줄지 않는다. 그래서 서버가 줄여 주는 시간은 폴링 간격 15초 정도뿐이다.

동작 규칙:
- 사장님이 쓰면: 멘션된 멤버 → 없으면 DM 상대 → 멤버 글에 단 스레드 답글이면 그 글쓴이 → 그 외에는 PM
- 멤버가 동료를 `{@role}`로 멘션하면 그 동료를 깨운다 (자기 자신 제외)
- 그 외의 사람이나 봇의 글은 아무도 깨우지 않는다
- 루프 방지: 역할당 시간당 20회, 멤버끼리 호출은 스레드당 시간당 8회까지. 넘으면 Sam이 스레드에 알리고 정기 작업에서 이어간다
- 개인정보: 저장소가 public이라 Actions 로그가 공개된다. 그래서 리스너는 Slack 본문을 로그나 실행 입력에 남기지 않고, 위치(채널, ts)만 넘긴다

## 반대 의견
- (예상되는 Ben의 반론) "어차피 언젠가 실시간이 필요하면 C를 처음부터 하는 게 낫지 않나?" → C는 사장님 계정의 외부 서비스와 Slack 앱 5개 재설정이 필요하다. A로 실제 대화 패턴을 먼저 보고 판단하는 게 싸다.
- 구독 사용량이 늘어난다. 대화가 많아질수록 실행 횟수가 늘기 때문이다. 루프 방지 상한과 `AGENT_MODEL` 비상 조절로 관리한다.

## 다시 볼 조건
- 리스너 공백이나 실패가 잦거나, 2~4분 반응이 대화에 방해가 된다는 피드백이 나오면 C를 ADR로 검토한다 (담당: 인프라 Sam, 백엔드 Ben)
- 구독 한도에 자주 닿으면 상한을 낮추거나 정기 작업 빈도를 줄인다
