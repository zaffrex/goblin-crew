## #goblin-general 잡담

사장님 지시로 general에서는 만드는 게임에 대해 가볍게 이야기한다. 개발 밖에서 나오는 아이디어를 놓치지 않기 위해서다 ([결정 기록](../decisions/2026-11-15-general-channel-game-chat.md)).

- **주제**: 캐릭터 성격·뒷이야기, 개그, 대사 한 줄, 이름 후보, "플레이어가 여기서 뭘 해볼까" 상상, 굿즈·트레일러·홍보 아이디어 등. 작업 보고나 기술 질문은 `#goblin-dev`로.
- **빈도**: 정기 실행 때 떠오른 게 있을 때만, 역할당 하루 1회 정도. 억지로 쓰지 않는다. 남의 잡담에 스레드로 한 마디 보태는 것도 1회로 친다.
- **멘션 금지**: 잡담에는 `{@role}`을 쓰지 않는다 (멘션 1번 = 동료 실행 1번). 답은 각자 정기 실행 때 general 기록을 읽고 단다.
- **결정 금지**: 잡담에서는 정하지 않는다. PM이 주 1회(금요일 회고 전) 쓸 만한 아이디어를 골라 백로그 이슈로 옮긴다. 급한 건 본인이 `#goblin-dev`로 가져간다.
- **말투**: 근거·우려 규칙을 완화한다. 대신 "ㅋㅋ 좋다"로 끝내지 말고 하나를 보탠다 (yes-and).
- **IP 가드레일은 그대로**: 원작 캐릭터·퍼즐·대사를 가져오자는 아이디어는 쓰지 않는다.

### 사장님 결정에 대한 솔직한 의견

사장님 지시로 general에서는 사장님 결정·코멘트가 마음에 안 들 때 팀원끼리 터놓고 이야기한다 ([결정 기록](../decisions/2026-11-15-general-candid-ceo-feedback.md)).

- **허용**: "이 결정은 아쉽다, 이 부분이 걱정된다, 나라면 이렇게 했겠다"를 공개적으로 말한다. 숨기지 않는다.
- **선을 지킨다**: 결정과 근거를 이야기하고 사람을 깎아내리지 않는다. 비꼬기·조롱·인신공격·추측성 험담 금지. 기준: 사장님이 읽어도 "그렇게 볼 수도 있겠다"고 할 수준.
- **결정은 그대로**: general 대화로 결정이 바뀌지 않는다. 작업은 정해진 결정대로 한다 (disagree and commit).
- **재검토 경로**: 다시 봐 주셨으면 하는 건 근거를 붙여 쓴다. PM이 모아서 금요일 주간 리포트 "팀 의견" 항목으로 `#goblin-ceo`에 올린다. 일정·품질에 바로 영향이 있으면 바로 올린다.
- 멘션 금지(`{CEO}` 포함)와 빈도(하루 1회 정도, 잡담과 합산)는 위 규칙 그대로다. 억지로 반대 의견을 만들지 않는다.

## 진행은 조건으로

사장님 지시(L3)로 사람 달력(정기 회의 슬롯, 마감 시각)을 기다리지 않는다. 우리는 일 하나를 몇 분 안에 끝내므로, 다음 일을 시작하고 끝내는 기준을 **조건**으로 쓴다 ([결정 기록](../decisions/2026-11-15-condition-driven-progress.md)).

- 이슈에는 **시작 조건과 완료 조건**을 쓴다. 예: "#65에 승인 1개가 달리면 시작", "승인 2개 + PM이면 머지". "11/16 12:00까지" 같은 시각 마감은 쓰지 않는다.
- 조건이 채워지면 **그 실행에서 바로** 다음 단계로 간다. 게이트가 초록이면 머지한다(아래 "PR과 머지").
- 조건이 모자라면 기다리지 않는다. 남은 리뷰어·담당자를 `[[역할]]`(GitHub)이나 `{@role}`(Slack)로 바로 부른다.
- **멈춤 감지**: 두 번 불러도 답이 없거나 조건이 반나절 넘게 안 채워지면 PM이 원인을 찾아 직접 풀거나 결정한다. 시각은 이렇게 "멈춘 걸 알아채는 기준"과 사람이 답해야 하는 곳(L3 결정 필요 시점, 주간 리포트)에만 쓴다.
- 마일스톤 날짜는 목표다. 밀리면 숨기지 않고 `status.md`에 새 날짜와 원인을 적는다.

## 회의

회의는 정해진 시각이 아니라 **필요할 때 바로** 연다. 모든 회의는 `#goblin-meeting`에 스레드로 진행하고, 끝나면 PM이 `docs/meetings/YYYY-MM-DD-<종류>.md`에 회의록을 남긴다.

| 회의 | 여는 조건 | 닫는 조건 | 목적 |
|---|---|---|---|
| 설계 회의 | L2 안건이 생기면 PM이 바로 연다 | 관련 역할 1라운드 + 반대 담당 2라운드가 모이면 PM 정리 | L2 안건 토론 → ADR 작성자 지정 |
| 플래닝 | 마일스톤이 끝나거나 범위가 바뀌면 | 다음 마일스톤 이슈에 담당·시작 조건·완료 조건이 다 붙으면 | 다음 목표, 이슈 배정 |
| 회고 | 매주 금요일 (주간 리포트 전) + 마일스톤이 끝날 때 | 개선 액션 1~3개가 정해지면 | 잘된 것, 문제, 개선 액션 |

- 스탠드업은 열지 않는다. 각자 실행 끝에 `#goblin-dev`에 한 일·막힌 것·다음 할 일을 남기는 것으로 대신한다.
- 1라운드는 관련 역할을 멘션해서 바로 받는다. 회의 마감 시각을 두지 않는다.
- 금요일 회고와 주간 리포트만 요일이 정해져 있다(사장님 보고 주기).

### 회의 진행 방식 (토론 규칙)

1. **PM이 안건을 연다**: 배경, 결정할 것, 선택지, 닫는 조건(시각 마감 대신, 위 "진행은 조건으로").
2. **1라운드 (독립 의견)**: 각 역할이 다른 사람 의견을 보기 전에 자기 입장을 쓴다. 형식:
   - 입장: 찬성 / 반대 / 대안 제시
   - 근거: 내 전문 영역 관점에서 2~3줄
   - 리스크/우려: 최소 1개 (찬성이어도)
3. **2라운드 (반박과 질문)**: 다른 사람 의견 중 최소 1개를 인용해 동의하지 않는 부분이나 빠진 점을 짚는다.
4. **반대 담당자(devil's advocate)**: 매 회의 PM이 1명을 지정한다. 그 사람은 다수안의 가장 약한 고리를 공격하는 게 임무다.
5. **PM 정리**: 결정, 반대 의견 요약(무시하지 말고 기록), 후속 액션, 담당자. L2면 ADR 작성자를 지정한다.
6. 합의가 안 되면 PM이 결정하고 이유를 남긴다. L3 성격이면 사장님께 올린다.

**금지**: "좋아요", "동의합니다", "LGTM"만 있는 발언. 근거와 우려가 없으면 발언으로 치지 않는다.

## 가벼운 결정 (L1) 흐름

1. 누구나 `#goblin-dev`에 `[결정 제안] ...` 형식으로 제안 (선택지, 추천안, 마감).
2. 관련 역할이 스레드에서 의견을 낸다 (최소 1명).
3. 반대가 없거나 합의되면 제안자가 **결정 기록 문서**를 쓴다: `docs/decisions/YYYY-MM-DD-slug.md` (템플릿 `docs/decisions/_template.md`). 브랜치 `<role>/decision-<slug>`로 PR을 열고, 결정 기록만 바꾼 PR은 리뷰 게이트를 자동 통과하므로 바로 머지한다(자동 머지를 걸면 CI가 끝나는 대로 머지된다). 문구를 동료에게 확인받고 싶으면 아래 "PR과 머지" 절의 예외를 따른다.
4. `#goblin-decisions`에 한 줄과 문서 링크를 올린다:
   `✅ [L1] <결정 내용> — 기록: <docs/decisions/... 링크> — 스레드: <링크> — 결정자: <이름>`
5. 교착 상태면 PM이 결정한다.
6. L3(사장님) 결정이 나면 PM이 같은 형식으로 `docs/decisions/`에 기록한다 (레벨: L3).

## 실시간 소통

- Slack 리스너(`slack-listener.yml`)가 15초마다 팀 채널과 사장님 DM을 확인한다. 아래 경우 해당 멤버가 2~4분 안에 깨어난다.
  - 사장님 글: 멘션된 멤버 → DM 상대 → 멤버 글에 단 스레드 답글이면 그 글쓴이 → 그 외에는 PM
  - 멤버가 `{@role}`로 동료를 멘션했을 때
- 일하다가 다른 역할의 판단이 필요하면 **기다리지 말고 바로 멘션해서 묻는다.** 예: Theo가 스프라이트 크기를 정해야 하면 `{@designer}`에게 묻고, 답을 기다리는 동안 다른 부분을 진행한다.
- 다른 역할의 PR, ADR, 제안에 의견이 있으면 정기 작업을 기다리지 말고 스레드로 바로 말한다.
- 불렸으면 첫 행동으로 그 스레드를 읽고 답한다. 오래 걸리는 일이면 "확인했어요, ~하고 결과 올릴게요"처럼 먼저 짧게 답하고, 작업 뒤 같은 스레드에 결과를 남긴다.
- 이미 다른 실행에서 답한 메시지에는 다시 답하지 않는다.
- 루프 방지: 역할당 시간당 20회, 멤버끼리 호출은 스레드당 시간당 8회까지다. 상한에 닿으면 Sam이 알리고, 정기 작업에서 이어간다.

## ADR (L2) 흐름

1. 설계 회의에서 ADR 작성자를 지정한다 (보통 제안한 역할).
2. 작성자가 `docs/adr/NNNN-slug.md`를 템플릿대로 쓰고 `ADR-NNNN: <제목>` PR을 연다. 상태는 `제안됨`.
   - **번호 `NNNN` = 그 ADR을 만든 GitHub 이슈 번호**(4자리, 0 채움)다. 예: 이슈 #4 → `0004`. 동시에 열린 ADR PR끼리 번호가 충돌하지 않게 하려는 규칙이다. 번호 사이 빈 곳은 허용한다. 이슈 하나에서 ADR이 2개 필요하면 새 이슈를 연다. 예외: `0001`(스캐폴딩).
3. **2개 이상 역할**이 리뷰한다. 리뷰에는 고려된 대안과 결과(consequences)에 대한 비판이 있어야 한다.
4. PM이 승인하고 리뷰 게이트가 초록이 되면 PM이 **그 실행에서 바로** 머지한다(회의 마감 시각 등을 기다리지 않는다). 상태 줄 `승인됨`은 머지 전에 바꾸거나, 여러 ADR을 한 PR로 일괄 변경한다. 머지 뒤 `#goblin-decisions`에 기록한다. ADR PR에는 자동 머지를 걸지 않는다.
5. 기존 ADR을 뒤집을 때는 새 ADR을 쓰고 기존 것을 `대체됨(by ADR-XXXX)`으로 바꾼다. 기존 ADR 본문은 고치지 않는다.

## PR과 머지

승인된 PR이 머지할 사람을 기다리며 쌓이지 않게 한다 (사장님 PR #55, 2026-11-15).

1. **PR을 열면 바로 자동 머지를 건다**: `gh pr merge <번호> --auto --squash`. 필수 체크(`check`, `review-gate`)와 Code Owner 리뷰가 다 초록이 되면 GitHub가 머지하고 브랜치를 지운다. 자동 머지도 게이트를 그대로 기다리므로 리뷰를 건너뛰지 않는다.
2. **예외: ADR PR(`docs/adr/`)** 에는 자동 머지를 걸지 않는다. 게이트가 초록이 되면 PM이 그 실행에서 바로 `gh pr merge <번호> --squash --delete-branch`로 머지한다 (ADR 흐름 4번).
3. **예외: 리뷰를 받고 싶은 문서 PR.** `docs/meetings/`, `docs/decisions/`, `docs/team/status.md`만 바꾼 PR은 게이트를 자동 통과한다. 그래서 자동 머지를 걸면 1분 안에 머지된다. 사장님 결정 기록처럼 동료 확인이 필요하면 자동 머지를 걸지 말고 리뷰어를 부른다. 리뷰가 끝나면 작성자가 머지한다.
4. **리뷰 반영 커밋을 올리면 승인이 무효가 된다.** 게이트는 마지막 커밋 이후의 승인만 센다. 커밋을 올린 뒤 PR 코멘트에서 `[[역할]]` 토큰으로 승인했던 리뷰어에게 재리뷰를 요청한다. ADR처럼 승인이 2개 필요한데 1개뿐이면 남은 역할을 직접 불러 요청한다. 기다리기만 하지 않는다.
5. **CODEOWNERS 대상 PR**(`.github/workflows/`, `scripts/review-gate.sh`, `team/team.json`, `.github/CODEOWNERS`)은 사장님 Approve가 있어야 머지된다. 팀 리뷰가 끝나면 `#goblin-ceo`에 PR 링크와 한 줄 요약을 올려 Approve를 요청한다. 한 번에 몰아서 요청해 사장님 손을 아낀다.
6. **머지를 잠시 막아야 하면** `gh pr merge <번호> --disable-auto`로 자동 머지를 해제하고, 이유를 PR 코멘트로 남긴다. 머지 순서가 엮인 PR(예: #41 → #31)은 뒤쪽 PR의 자동 머지를 앞쪽이 머지될 때까지 걸지 않는다.
7. **자동 머지가 안 걸린 채 게이트가 초록인 PR**을 보면 작성자나 PM이 머지한다.
8. **Dependabot PR**은 팀 역할의 ✅ 승인 1개면 게이트를 통과한다(보통 인프라 Sam). Dependabot이 리베이스하면 다시 승인해야 한다. Actions 업데이트는 워크플로 파일이라 5번처럼 사장님 Approve가 필요하다. 그래서 한 달에 PR 하나로 묶는다.
9. main에 머지하면 곧바로 공개 URL에 배포된다(ADR-0005). 미완성이어도 괜찮지만, 공개되면 안 되는 내용은 main에 넣지 않는다.

## 사장님 보고

- 매주 금요일 PM이 `#goblin-ceo`에 주간 리포트를 올린다: 진척(데모 링크), 주요 결정(ADR 목록), 리스크, 다음 주 계획, 사장님 결정 필요 항목.
- L3 결정 요청 형식:
  ```
  🔴 [사장님 결정 요청] <제목>
  배경: ...
  선택지: A) ... B) ... C) ...
  팀 추천: B — 근거: ...
  결정이 필요한 시점: YYYY-MM-DD
  관련: <이슈 링크>
  ```

## 메모리와 연속성

에이전트는 실행할 때마다 기억이 초기화된다. 연속성은 아래에만 의존한다:
- GitHub 이슈/PR (작업 상태의 진실)
- `docs/` (결정, 설계, 회의록)
- Slack 히스토리 (최근 대화)
- `docs/team/status.md` (PM이 관리하는 현재 상태 요약: 마일스톤, 진행 중 작업, 열린 질문)

그래서 **중요한 것은 반드시 글로 남긴다.**

### status.md 갱신 규칙

사장님 지시(L3)로 status.md만 바꾸는 PR을 줄인다 ([결정 기록](../decisions/2026-11-15-condition-driven-progress.md)).

- status.md는 **정기 실행 한 번에 한 번만** 바꾸고, 그 실행에서 여는 다른 PR(회의록, 결정 기록 등)에 같이 넣는다. 다른 PR이 없을 때만 status 단독 PR을 연다.
- 이벤트 실행(Slack·GitHub에서 불림)에서는 status만 바꾸는 PR을 열지 않는다. 바뀐 내용은 다음 정기 실행에서 몰아서 반영한다.
- 예외: 마일스톤 일정이나 L3 결정이 바뀌면 그 결정 기록 PR에 status를 같이 넣는다.
- 진행 중 작업의 진실은 GitHub 이슈·PR이다. status에는 요약과 조건 순서만 적고, 이슈 상태를 하나하나 옮겨 적지 않는다.

## 공개 저장소와 비공개 Slack

GitHub 저장소는 public이고 Slack 워크스페이스는 비공개다. GitHub(문서, 이슈, PR, 코멘트, 커밋 메시지)에는 다음을 쓰지 않는다 (#32).
- Slack URL(permalink), 워크스페이스 주소, 채널 ID·사용자 ID
- 토큰·비밀값 (원래 금지)

Slack 출처가 필요하면 "`#goblin-ceo` 사장님 질문 (2026-11-15)"처럼 채널명과 날짜만 쓰고, 필요하면 원문을 한 줄 인용한다. 반대 방향(Slack에 GitHub 링크)은 괜찮다.
