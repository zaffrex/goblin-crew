# 팀 운영 매뉴얼

## Slack 채널

| 채널 | 용도 |
|---|---|
| `#goblin-general` | 게임 잡담, 개발 외 아이디어, 공지 (아래 "#goblin-general 잡담") |
| `#goblin-dev` | 작업 진행 보고, 기술 질문, 가벼운 결정(L1) 스레드 |

## #goblin-general 잡담

사장님 지시로 general에서는 만드는 게임에 대해 가볍게 이야기한다. 개발 밖에서 나오는 아이디어를 놓치지 않기 위해서다 ([결정 기록](../decisions/2026-11-15-general-channel-game-chat.md)).

- **주제**: 캐릭터 성격·뒷이야기, 개그, 대사 한 줄, 이름 후보, "플레이어가 여기서 뭘 해볼까" 상상, 굿즈·트레일러·홍보 아이디어 등. 작업 보고나 기술 질문은 `#goblin-dev`로.
- **빈도**: 정기 실행 때 떠오른 게 있을 때만, 역할당 하루 1회 정도. 억지로 쓰지 않는다. 남의 잡담에 스레드로 한 마디 보태는 것도 1회로 친다.
- **멘션 금지**: 잡담에는 `{@role}`을 쓰지 않는다 (멘션 1번 = 동료 실행 1번). 답은 각자 정기 실행 때 general 기록을 읽고 단다.
- **결정 금지**: 잡담에서는 정하지 않는다. PM이 주 1회(금요일 회고 전) 쓸 만한 아이디어를 골라 백로그 이슈로 옮긴다. 급한 건 본인이 `#goblin-dev`로 가져간다.
- **말투**: 근거·우려 규칙을 완화한다. 대신 "ㅋㅋ 좋다"로 끝내지 말고 하나를 보탠다 (yes-and).
- **IP 가드레일은 그대로**: 원작 캐릭터·퍼즐·대사를 가져오자는 아이디어는 쓰지 않는다.

## 정기 회의

모든 회의는 `#goblin-meeting`에 스레드로 진행하고, 끝나면 PM이 `docs/meetings/YYYY-MM-DD-<종류>.md`에 회의록을 남긴다.

| 회의 | 주기 | 참석 | 목적 |
|---|---|---|---|
| 데일리 스탠드업 | 매일 1회 | 전원 | 어제 한 일, 오늘 할 일, 막힌 것 |
| 설계 회의 | 주 2회 (월·목) | 전원 | L2 안건 토론 → ADR 초안 담당자 지정 |
| 스프린트 플래닝 | 주 1회 (월) | 전원 | 이번 주 목표, 이슈 배정 |
| 회고 | 주 1회 (금) | 전원 | 잘된 것, 문제, 개선 액션 1~3개 |

### 회의 진행 방식 (토론 규칙)

1. **PM이 안건을 연다**: 배경, 결정할 것, 선택지, 마감.
2. **1라운드 (독립 의견)**: 각 역할이 다른 사람 의견을 보기 전에 자기 입장을 쓴다. 형식:
   - 입장: 찬성 / 반대 / 대안 제시
   - 근거: 내 전문 영역 관점에서 2~3줄
   - 리스크/우려: 최소 1개 (찬성이어도)
3. **2라운드 (반박과 질문)**: 다른 사람 의견 중 최소 1개를 인용해 동의하지 않는 부분이나 빠진 점을 짚는다.
4. **반대 담당자(devil's advocate)**: 매 회의 PM이 1명을 지정한다. 그 사람은 다수안의 가장 약한 고리를 공격하는 게 임무다.
5. **PM 정리**: 결정, 반대 의견 요약(무시하지 말고 기록), 후속 액션, 담당자. L2면 ADR 작성자를 지정한다.
6. 합의가 안 되면 PM이 결정하고 이유를 남긴다. L3 성격이면 사장님께 올린다.

**금지**: "좋아요", "동의합니다", "LGTM"만 있는 발언. 근거와 우려가 없으면 발언으로 치지 않는다.

## 가벼운 결정 (L1) 흐름

1. 누구나 `#goblin-dev`에 `[결정 제안] ...` 형식으로 제안 (선택지, 추천안, 마감).
2. 관련 역할이 스레드에서 의견을 낸다 (최소 1명).
3. 반대가 없거나 합의되면 제안자가 **결정 기록 문서**를 쓴다: `docs/decisions/YYYY-MM-DD-slug.md` (템플릿 `docs/decisions/_template.md`). 브랜치 `<role>/decision-<slug>`로 PR을 열고, 결정 기록만 바꾼 PR은 리뷰 게이트를 자동 통과하므로 바로 머지한다.
4. `#goblin-decisions`에 한 줄과 문서 링크를 올린다:
   `✅ [L1] <결정 내용> — 기록: <docs/decisions/... 링크> — 스레드: <링크> — 결정자: <이름>`
5. 교착 상태면 PM이 결정한다.
6. L3(사장님) 결정이 나면 PM이 같은 형식으로 `docs/decisions/`에 기록한다 (레벨: L3).

## 실시간 소통

- Slack 리스너(`slack-listener.yml`)가 15초마다 팀 채널과 사장님 DM을 확인한다. 아래 경우 해당 멤버가 2~4분 안에 깨어난다.
  - 사장님 글: 멘션된 멤버 → DM 상대 → 멤버 글에 단 스레드 답글이면 그 글쓴이 → 그 외에는 PM
  - 멤버가 `{@role}`로 동료를 멘션했을 때
- 일하다가 다른 역할의 판단이 필요하면 **기다리지 말고 바로 멘션해서 묻는다.** 예: Theo가 스프라이트 크기를 정해야 하면 `{@designer}`에게 묻고, 답을 기다리는 동안 다른 부분을 진행한다.
- 다른 역할의 PR, ADR, 제안에 의견이 있으면 정기 작업을 기다리지 말고 스레드로 바로 말한다.
- 불렸으면 첫 행동으로 그 스레드를 읽고 답한다. 오래 걸리는 일이면 "확인했어요, ~하고 결과 올릴게요"처럼 먼저 짧게 답하고, 작업 뒤 같은 스레드에 결과를 남긴다.
- 이미 다른 실행에서 답한 메시지에는 다시 답하지 않는다.
- 루프 방지: 역할당 시간당 20회, 멤버끼리 호출은 스레드당 시간당 8회까지다. 상한에 닿으면 Sam이 알리고, 정기 작업에서 이어간다.

## ADR (L2) 흐름

1. 설계 회의에서 ADR 작성자를 지정한다 (보통 제안한 역할).
2. 작성자가 `docs/adr/NNNN-slug.md`를 템플릿대로 쓰고 `ADR-NNNN: <제목>` PR을 연다. 상태는 `제안됨`.
   - **번호 `NNNN` = 그 ADR을 만든 GitHub 이슈 번호**(4자리, 0 채움)다. 예: 이슈 #4 → `0004`. 동시에 열린 ADR PR끼리 번호가 충돌하지 않게 하려는 규칙이다. 번호 사이 빈 곳은 허용한다. 이슈 하나에서 ADR이 2개 필요하면 새 이슈를 연다. 예외: `0001`(스캐폴딩).
3. **2개 이상 역할**이 리뷰한다. 리뷰에는 고려된 대안과 결과(consequences)에 대한 비판이 있어야 한다.
4. PM이 승인하면 상태를 `승인됨`으로 바꾸고 머지한 뒤 `#goblin-decisions`에 기록한다.
5. 기존 ADR을 뒤집을 때는 새 ADR을 쓰고 기존 것을 `대체됨(by ADR-XXXX)`으로 바꾼다. 기존 ADR 본문은 고치지 않는다.

## 메모리와 연속성

에이전트는 실행할 때마다 기억이 초기화된다. 연속성은 아래에만 의존한다:
- GitHub 이슈/PR (작업 상태의 진실)
- `docs/` (결정, 설계, 회의록)
- Slack 히스토리 (최근 대화)
- `docs/team/status.md` (PM이 관리하는 현재 상태 요약: 마일스톤, 진행 중 작업, 열린 질문)

그래서 **중요한 것은 반드시 글로 남긴다.**

## 공개 저장소와 비공개 Slack

GitHub 저장소는 public이고 Slack 워크스페이스는 비공개다. GitHub(문서, 이슈, PR, 코멘트, 커밋 메시지)에는 다음을 쓰지 않는다 (#32).
- Slack URL(permalink), 워크스페이스 주소, 채널 ID·사용자 ID
- 토큰·비밀값 (원래 금지)

Slack 출처가 필요하면 "`#goblin-ceo` 사장님 질문 (2026-11-15)"처럼 채널명과 날짜만 쓰고, 필요하면 원문을 한 줄 인용한다. 반대 방향(Slack에 GitHub 링크)은 괜찮다.
