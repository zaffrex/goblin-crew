# M1 판정 절차 (수직 슬라이스: 화면 1 `magpie_nest`)

- 작성: **[PM Noah]**, 2026-11-15 (#85)
- 상태: 운영 문서. 판정 기준 숫자를 바꾸는 건 L1(PM 결정 + 결정 기록), 판정 결과로 퍼즐 원칙을 바꾸는 건 L2(ADR).
- 관련: `docs/team/status.md` M1 표, #71 이후 게이트 3, ADR-0018 "다시 검토할 조건", `docs/design/fun-checklist.md`

## 왜 따로 적나

M1 판정은 두 가지를 본다. **(가) 끝까지 돌아가는가**와 **(나) 재미있는가**. (가)는 에이전트가 판정할 수 있지만 (나)는 사람만 할 수 있다. 그리고 에이전트는 브라우저를 손으로 누를 수 없다. 그래서 누가 무엇을 어떻게 확인하는지 미리 정해 둔다.

## 시작 조건

아래가 모두 채워지면 PM이 **그 실행에서 바로** 판정을 시작한다. 날짜를 기다리지 않는다.

1. #65(데이터 모델 ADR), #64(코어 엔진), #66(화면 1 설계 + JSON), #67(BFS 검사), #68(상호작용 UI)이 머지됐다.
2. main의 `deploy`가 성공했고, 배포 URL에서 화면 1이 열린다.
3. CI의 BFS 검사가 화면 1 데이터로 통과했다(ADR-0018 실패 항목 0개, 경고는 PR에 이유가 있음).

## 판정 1: 끝까지 돌아가는가 (에이전트)

**방법: 배포 URL을 headless Chrome에서 열고, 실제 입력 이벤트로 `solution`을 재생한다.** 단위 테스트(`step` 함수)만으로는 안 된다. 히트 박스, 입력 처리, 말풍선이 정답 클릭을 가리는 문제는 실제 빌드에서만 보인다.

- 도구: `scripts/playtest/` (PM이 만든다. #65에서 화면 데이터 형식이 정해진 뒤 별도 PR). Chrome DevTools Protocol로 마우스 클릭과 터치 탭을 보내고, 행동마다 스크린샷을 남긴다. 클릭 좌표는 화면 JSON의 핫스팟·서는 자리에서 계산한다. 엔진 내부 함수를 직접 부르지 않는다.
- 뷰포트 2개: 데스크톱 1280×720(마우스), 모바일 390×844 세로(터치 탭). 모바일 가로는 M2.

| # | 확인 | 통과 기준 |
|---|---|---|
| A1 | 정답 재생 | 데스크톱·모바일 모두 커밋된 `solution` 그대로 클리어 컷까지 간다 |
| A2 | 실패 반응 | 정답에 가까운 오답 1개 이상에서 고유 실패 반응이 보인다(스크린샷) |
| A3 | 게이지 0 | 일부러 실패를 반복해 게이지를 0으로 만들면 "퇴근 못 하겠다" 컷 → 서는 자리만 리셋 → 이어서 클리어할 수 있다(ADR-0018 G2, S3) |
| A4 | 콘솔 | 재생 내내 콘솔 에러 0개 |
| A5 | 첫 화면 | 첫 화면이 3초 안에 뜬다(headless, 캐시 없음. 기준은 시작값) |

- **PM과 Luna가 각자 따로** 재생 결과(스크린샷)를 보고 판정한다. Luna는 스크린샷이 #66 설계와 같은지(반응, 대사, 가림 순서)를 본다.
- A1~A4 중 하나라도 실패하면 버그 이슈를 열고(`type:bug`, `prio:p0`) 판정을 멈춘다. 고친 PR이 머지되면 처음부터 다시 재생한다. A5만 실패하면 경고로 기록하고 진행한다.

## 판정 2: 재미있는가 (사장님)

#71 이후 게이트 3에 따라 사장님이 배포 URL에서 직접 플레이한다. 판정 1이 통과한 뒤 PM이 `#goblin-ceo`에 요청한다.

- 요청에 담을 것: 배포 URL, "힌트 없이 해 보시고, 막히면 막힌 채로 알려 주세요", 아래 질문 5개. 공략은 보내지 않는다.
- 사장님 시간을 아끼려고 질문은 5개만 한다. 답이 짧아도 된다.

1. 끝까지 깼나요? 못 깼다면 어디서 멈췄나요?
2. 웃긴 순간이 있었나요? 어떤 반응이었나요?
3. 짜증 난 순간이 있었나요?
4. 위쪽 게이지(보송 게이지)가 신경 쓰였나요? 아예 안 봤나요?
5. 이 화면이 4개 더 있으면 해 보고 싶나요?

- 기다리는 동안 팀은 판정에 막히지 않는 일(첫 실제 스프라이트, M2 화면 매트릭스, #77)을 한다. 화면 2~5 **상세 설계**는 사장님 답이 오기 전에 시작하지 않는다(재설계가 나면 버려지므로).

## 관찰을 어디에 남기나

- 판정 결과는 이슈 하나(`M1 판정 결과`, `role:pm`)에 아래 양식으로 남긴다. Slack에서만 끝내지 않는다.
- 사장님 답은 Slack 원문을 그대로 옮기지 않고 요약해 적는다(출처: `#goblin-ceo` + 날짜).
- 재미 관찰은 `docs/design/fun-checklist.md`의 해당 항목(C1~C12, X1 등)에 연결한다. 효과가 확인된 항목만 ADR-0018 후속 ADR로 올린다(fun-checklist "다음").

## 리스크

- **자동 재생은 "사람이 깰 수 있나"를 증명하지 않는다.** 정답을 아는 스크립트는 단서가 약해도 깬다. 그래서 단서·재미 판단은 판정 2에만 맡긴다. 사장님 답이 늦으면 M1이 닫히지 않는다. 그래도 M1 날짜 때문에 판정 2를 건너뛰지 않는다(사장님 방침: 일정보다 디테일 품질).
- 재생 도구를 만드는 시간이 M1 임계 경로에 들어갈 수 있다. #65 머지 직후 시작해서 #68과 병렬로 만든다. 도구가 늦으면 대안은 headless 스크린샷 + `step` 리플레이 테스트지만, 이 경우 A1은 "조건부 통과"로 적는다.
- 피험자가 사실상 사장님 한 명이다. 한 사람 감상으로 퍼즐 원칙(ADR)을 바꾸지 않는다. 원칙 변경은 M2 화면에서 같은 관찰이 다시 나올 때 한다.
